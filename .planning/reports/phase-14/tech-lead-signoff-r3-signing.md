## C. Ruling 1 — the `contains("elease")` heuristic: NARROW THE PREDICATE, KEEP THE THROW

The auditor offered two remedies for F-1: drop the configuration-time throw for signing and rely on `verifyReleaseSigning`, or narrow the throw to names that actually package. **I take the second, in a form that is neither an exhaustive task list nor a loosening, and I reject the first.**

**Why not drop the throw.** It is the cheapest edit and it is the wrong one. The configuration-time throw is the *only* thing that tells an operator in two seconds that they forgot to export a variable; `verifyReleaseSigning` is strictly tighter about *coverage* but strictly worse about *latency*, because on `assembleRelease` it fires after compilation and R8. Trading a 2-second failure for a 3-minute one, on the single command the whole gate exists for, to fix a complaint about a *different* command, is a bad exchange. It also leaves the gate's correctness resting on one `tasks.matching { it.name == "packageRelease" }` block, whose silent-on-no-match behaviour the developer deliberately chose as a *belt* and which would become the only braces.

**The ruling.** `app/build.gradle.kts:88-92` becomes a verb-prefix test rather than a substring test:

```kotlin
// Names that actually PACKAGE a release variant. A prefix-verb test, not an exhaustive
// task list: forgetting a name in a list is a silent hole, whereas a new packaging task
// that does not start with one of these verbs does not exist in AGP's naming scheme.
val releasePackagingVerbs = setOf("assemble", "bundle", "package", "install", "publish")
val isReleaseInvocation =
    gradle.startParameter.taskNames.any { requested ->
        val name = requested.substringAfterLast(':')
        name in wholeProjectTaskNames ||
            (name.contains("elease") && releasePackagingVerbs.any { name.startsWith(it) })
    }
```

This keeps `assembleRelease`, `bundleRelease`, `packageRelease`, `packageReleaseBundle`, `installRelease`, `publishReleaseBundle…` and the three whole-project names, and drops `lintRelease`, `lintVitalRelease`, `detektRelease`, `compileReleaseKotlin`, `connectedReleaseAndroidTest` and every future analysis task whose name happens to contain the substring. I prefer it to an enumerated name list for one reason: a forgotten entry in a list is a silent hole, while a packaging task outside AGP's five verbs is not a thing that exists.

**It is a three-gate change, not a signing change, and that is the part that needs care.** `isReleaseInvocation` is shared by the ad-ID gate (`:110`), the Play-Games-ID gate (`:141`) and the new signing gate (`:178`). Narrowing it therefore also stops `./gradlew :app:lintRelease` failing on missing ad IDs — which is safe *only because* the execution-time backstops cover the packaging path. Today they do for signing and do not properly for the two ID domains, which is exactly ruling 2. **So rulings 1 and 2 are one task and must not be split**: narrowing the configuration gate without tightening the ID hooks would weaken PLAT-06/D-05 and D-17, and that I would reject.

**It also falsifies a comment in the file R-1 edits.** `standards.gradle.kts:53-54` gives as one of four reasons for the F-1 detekt design: "`detektRelease`'s NAME matches `app/build.gradle.kts`'s `contains("elease")` ad-ID guard, so it cannot be invoked directly without real AdMob IDs." After this ruling that sentence is false and `detektRelease` becomes directly invocable. The F-1 design is unaffected — my predecessor already recorded reason 1 (this plugin is applied to `:domain`, where the variant tasks do not exist) as decisive on its own — but the comment must be corrected in the same change, and correcting it is what makes this ruling part of R-1 rather than a fourth branch in the same file.

**Ships before the release branch: yes.** Not because of F-1's security-usability argument on its own — that is real but it is a Medium — but because ruling 2 rides with it and ruling 2 is now a genuine hole. Cost is one predicate, two comments and the one line in ruling 2. It is **not** a blocker for merging either branch under review.

## D. Ruling 2 — `verifyReleaseAdIds` / `verifyReleaseGamesIds` on the lifecycle task only: A REAL HOLE, AND BRANCH B IS WHAT MADE IT ONE

**Yes, the asymmetry is a real hole, and it was not one last week.** `app/build.gradle.kts:247-248` hangs both ID checks off `assembleRelease`/`bundleRelease`, which are *lifecycle* tasks: a dependency of a lifecycle task is a sibling of the package task, and Gradle may order the two either way. The auditor measured the bad ordering — in a `bundleRelease` dry run the two ID checks are listed **after** `packageReleaseBundle`, while `verifyReleaseSigning` (`:258-259`) is listed immediately before it.

The consequence used to be tolerable and no longer is. Before branch B, the artifact produced in that window was **unsigned**: `app-release-unsigned.apk`, an object nobody could upload even by accident. After branch B, with the founder's real keystore exported — which is precisely the state the release procedure puts the machine in — the same window produces `app/build/outputs/bundle/release/app-release.aab`, **signed with the real upload key and carrying `UNRESOLVED-see-local.properties.template` in `BuildConfig`**, sitting on disk after a build that then failed. That is the exact shape of the auditor's own F-3 ("that is precisely the artifact that gets uploaded by accident"), one grade worse, because this one is signed. The developer's report says it declined to change the ID hooks because "it is not this task" — correct under standing rule 4, and correct to route it to me.

**The ruling.** Add the two ID checks to the package-task hook, so `app/build.gradle.kts:258-259` reads:

```kotlin
tasks.matching { it.name == "packageRelease" || it.name == "packageReleaseBundle" }.configureEach {
    dependsOn(verifyReleaseAdIds, verifyReleaseGamesIds, verifyReleaseSigning)
}
```

The lifecycle hook at `:247-248` stays as written, for the reason the developer gave and I endorse: `matching {}` is silent when a name does not exist, so if a future AGP renames the package tasks the checks still run late rather than vanishing. Two hooks, belt and braces, one line changed.

**Verification bar, same standard my predecessor set for F-8 and including the negative control:** with the four `PLAY_UPLOAD_*` variables exported to a **throwaway** key and the ad/PGS IDs deliberately absent, run `./gradlew -m :app:bundleRelease` and `-m :app:assembleRelease` and confirm all three verify tasks are listed **before** `packageReleaseBundle` / `packageRelease`; then run them for real and confirm **no file appears** under `app/build/outputs/`. Negative control: with everything correct, confirm the artifact is produced and `apksigner`/`jarsigner` verify it. The founder's real key must not be used for any of this.

**When: the same task as ruling 1, before the release branch is cut.** The signed-build procedure (`14-RELEASE-PLAN.md` §4b) is run on the release branch with the real key exported, which is the one moment this hole is live. It does not block either merge.

**One low-priority third line, bounded.** The auditor's F-2 observes that AGP's own `validateSigningRelease` reports a mistyped keystore path first, printing the absolute path, which makes `SigningKeystoreProbe`'s nicer missing-file message effectively unreachable on `assembleRelease` — the two tasks are siblings and the ordering is arbitrary. A path is not a cryptographic secret and no artifact is produced, so this is diagnostics, not security. If `tasks.matching { it.name == "validateSigningRelease" }.configureEach { dependsOn(verifyReleaseSigning) }` costs one line and works, take it in the same task; **if it fights AGP in any way, stop and report rather than growing the task.**

## E. Ruling 3 — F-14: QA's correction is right, MEDIUM as a determinism defect, and it is a two-stage fix

**I accept QA's correction in full and it is the more accurate reading of the code.** I read `AppForegroundTrackerTest.kt:66-95` myself rather than taking either report's word for it:
- `:73` — `store.lastForegroundAtMs.first { it >= before }`, where `before` is the test's `System.currentTimeMillis()` at `:70` and the compared value comes from the *tracker's own independent* clock read inside `onStop`. An **open** predicate with no bound.
- `:92` — `store.state.first { it.firstSessionComplete }`, which becomes true only if the tracker's `now'` satisfies `now' ≥ now − SETTLE_MARGIN_MS`. Also open.

A `first { }` whose predicate becomes unsatisfiable does not fail an assertion; it suspends until `runTest`'s real-time 60-second timeout kills it, producing an `UncompletedCoroutinesError` **indistinguishable at the console from F-10's**. So these are not, as the auditor framed them, latent assertion flakes with seconds of margin. They are residual hang paths.

**QA is also right on the direction of the margin at `:92`, and the auditor had it backwards.** `SETTLE_MARGIN_MS = 1_000` is absorbing a *backwards* clock step, not a forward stall — a forward stall makes `now' − leftAt ≥ SESSION_GAP_MS` hold *more* strongly. The auditor's "only a stall of over a second could flip it" has the sign wrong for this site. The trigger for both sites is the wall clock moving backwards (an NTP step or a manual clock change), not load.

**Severity: MEDIUM as a test-determinism defect, LOW as a release risk.** Medium because it is a literal violation of `rules/testing.md`'s one-sentence rule and because its *symptom* is the same 60-second mystery that cost this phase a release-gate scare; low as release risk because the trigger is a backwards clock step between two adjacent statements, which is orders of magnitude rarer than F-10's 21.7 %. QA explicitly declined to raise it to a release blocker and I agree. It does not hold either branch and it does not hold the branch cut.

**`ResultsViewModelTest:1624` — not a violation today; QA's reasoning is correct and I adopt it.** I read the fixture: `now` is captured once and the same constant drives the seeding, the transition and the predicate, and `mayShow(nowMs: Long)` takes its instant as a parameter and reads no clock. It is a clock *read*, not a clock *dependency*; it cannot hang and it cannot flake. It should go with the injected clock for the rule's letter and for uniformity, and it carries no risk until then. QA's line-number correction (`:1608` → `:1624`, shifted by the `develop` merge at `82ff777`) is confirmed.

**The ruling — two stages, and the cheap one is not the one the auditor named.**
1. **Now, test-only, non-gating: bound the two open awaits.** Wrapping `:73` and `:92` in `withTimeout(…)` inside `runTest` costs two lines and no production risk, and — because `withTimeout` inside `runTest` runs on **virtual** time — it converts a 60-second real-time mystery into an immediate, named `TimeoutCancellationException` at a known line. That is a strict improvement in diagnosability at effectively zero cost and zero blast radius, and it does not pretend to be the fix. Fold it into the test-hygiene task in ruling 4; if `withTimeout` interacts badly with `backgroundScope`'s `stateIn` in a way I have not foreseen, the developer **stops and reports** rather than growing the task.
2. **After v1.1: the injected clock in `AppForegroundTracker`.** This is the honest fix and it is production source. `AppForegroundTracker` is a two-method `@Singleton` that `App.onCreate` injects concretely, and the change is a constructor-injected time source plus a Hilt binding plus the test updates — small, but it re-cuts the **interstitial session boundary**, which is what D-04's per-session cap is measured from, and whose physical-device confirmation of assumption A1 is still open per the class's own KDoc. Changing the clock source of the one mechanism that limits how many ads a long sitting can produce, days before a first release, is a worse risk than a hang that needs the wall clock to step backwards. **Scheduled post-v1.1, with QA's rationale attached verbatim.**
3. **The standing exception, and it is the sentence worth keeping:** if a 60-second `UncompletedCoroutinesError` is seen in this suite again before the tag, `AppForegroundTrackerTest` is the first place to look and stage 2 is promoted immediately. That is QA's operational note and it is the reason this section exists.
