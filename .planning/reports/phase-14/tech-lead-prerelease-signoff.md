## C. F-10 — the DataStore test flake: RULED

**Is the auditor's mechanism the likeliest one? Its *class* is right and its *variant* is a hypothesis — and for once the difference does not matter for the decision.**
- The developer's diagnosis is ruled out, and the auditor's arithmetic is the reason: 0.005 s against 60.041 s is four orders of magnitude. Worker contention turns 5 ms into 50 ms; it does not produce `UncompletedCoroutinesError: After waiting for 1m`. That figure is `runTest`'s real-time timeout expiring on a **hung** body, not a slow one.
- The enabling condition is certain and is enough to condemn the pattern on its own: `PreferenceDataStoreFactory.create` with no `scope` runs real file IO on DataStore's own `Dispatchers.IO` scope, outside `runTest`'s virtual clock, while the body waits against a wall-clock timeout. `rules/testing.md` forbids that in one sentence — "Deterministic tests only: no wall-clock, no network, no unseeded random, no sleeps."
- The auditor's specific mechanism — two eager `stateIn` collectors on the single-threaded test dispatcher over one store whose actor lives on `Dispatchers.IO`, losing a wakeup — is plausible and is the best available explanation of *why this test and not the other nine*. It is unreproduced and I am not treating it as established. What is established is the class: a cross-dispatcher ordering dependency, not load. Both that variant and the simpler "body blocks in real time while the resumption needs the test scheduler" variant are cured by the same fix, so choosing the fix does not require the reproduction — which matters, because demanding that a 1-in-N 60-second hang be reproduced on demand before it may be fixed is how this ends up failing a release merge instead.

**Is the in-memory double the right fix? Yes, as the default, with a contract I am fixing here so the task is not blocked waiting on me.** It removes the wall clock, the temp file and the foreign scope in one move, and it loses nothing: no test in the ten classes asserts anything about the *file* — "killed and relaunched" is simulated by a second holder over the same store object, which a shared in-memory store reproduces exactly. Two conditions, because a helper used by ten classes is infrastructure:
1. The double must preserve the two semantics those tests actually rely on — `updateData`'s read-modify-write atomicity under concurrent callers, and `data` emitting the current value then subsequent updates — and it must carry **its own** small test class pinning both. An unverified fake under 10 classes and ~200 tests is a worse risk than the flake.
2. Any class that turns out to assert genuinely file-backed behaviour keeps a **real** store, but with an explicit `scope` tied to the test scheduler, and records in its KDoc why it is the exception. The helper is not forced on it, and that outcome is not a failure of the task.

I explicitly reject the developer's first instinct — "hand DataStore the test scope" — as the *primary* remedy, for the auditor's reason: if the mechanism is cross-dispatcher, moving the store's blocking IO onto the same single thread is as likely to change the symptom as to remove it. It is the fallback for case 2 only.

**Does it ship before the release branch? Yes — all ten classes, not one.** `rules/studio.md` makes "the repo's Check command passes locally" the definition of done and `rules/gitflow.md` makes Check-green a precondition of the release merge, so this failure mode can fail a release at the worst possible moment on a run nobody can reproduce; the studio forbids the cheap exits (no `@Ignore`, no disabled test, and I would reject a suppression here because a correct fix exists and is not expensive); and a partial migration leaves nine classes with the identical latent hang, for a marginal cost measured in hours of mechanical, fully reviewable edits. **Fallback, so this cannot itself become the thing that holds the release:** if the migration is not green after one review loop, the release-manager may cut the branch with the flaking class migrated and the remaining classes carried into v1.1.1 — but only on evidence of **10 consecutive green** full `:domain:test :app:testDebugUnitTest` runs at CI's worker count. That is a decision the release-manager may take without coming back to me.

**Who writes it.** **android-game-dev** writes the helper and migrates the ten classes — test sources are source, and the developer roles write tests. **qa-engineer** owns the reproduction attempt and the acceptance evidence: a bounded budget (say 20 full-suite runs under load, with a thread dump captured if it hangs) to try to pin the mechanism, then the determinism bar — N ≥ 10 consecutive green full-suite runs at CI's worker count, plus a grep proving no `PreferenceDataStoreFactory.create` without an explicit `scope` survives in test sources. A single green pass in isolation is not evidence about this failure mode. **code-auditor** reviews. Reproduction is *not* a precondition for the fix; if it does not reproduce inside the budget, the task proceeds and says so. I approve the helper's contract above as the tech-lead decision, so no one waits on a second round with me.
