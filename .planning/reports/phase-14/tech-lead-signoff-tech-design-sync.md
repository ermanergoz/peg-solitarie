### S-1 — `docs/release-checklist.md:32`, 1.1a condition (3): the "only merge-ins touched `app/` after `R`" test needs `--first-parent` (MINOR, safe direction, release-manager)
As written: `git log --no-merges --format=%h R..$M^2 -- app/` prints nothing. `R..$M^2` is every commit reachable from the branch head and not from `R`; a `develop` merge-in after `R` makes every `develop` commit since the last merge-in reachable, and `--no-merges` drops only the merge commits themselves, not what they brought. So on the exact path F-1 asked (3) to allow — check-gates or F-1 landing on `develop` first, TB merging `develop` in — the command prints `develop`'s own `app/` commits (C7's `:app` warning fixes, `ui/home/`), and (3) can never exit clean. Demonstrated on the one branch in the repo with a `develop` merge-in today, `feature/licences-screen` (merge-in `4069b53`, `R` = its first parent `ecddc40`, path `docs/` since that branch has no `app/` change): `git log --no-merges --format=%h ecddc40..feature/licences-screen -- docs/` → 7 commits, six of them `develop`'s (`ef721dd`, `a9534f6`, `d194acc`, `f2e7015`, `5f07005`, `364e78f`); with `--first-parent` → 1, the branch's own `2a058dd`. **Fix:** `git log --no-merges --first-parent --format=%h R..$M^2 -- app/` (with `--first-parent` the walk follows the branch's own line and stops at `R`; the merge-ins are excluded by `--no-merges`).
