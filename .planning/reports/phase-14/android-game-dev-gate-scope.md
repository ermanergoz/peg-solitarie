## What each ruling changed, and why it is shaped this way

**Ruling 1 — where the predicate lives.** The tech-lead's snippet was inline in `app/build.gradle.kts`. I kept its semantics **exactly** and moved it to `build-logic/ReleaseInvocation.kt`, because `app/build.gradle.kts` itself records why `AdIdResolution` and `SigningResolution` live there: AGP 9.1.0 creates a unit-test component only for the tested build type, so a release-gate assertion in `:app` would silently never run. A predicate that decides whether two cryptographic secrets are demanded is exactly the thing that should not rest on a dry run nobody repeats. If the auditor prefers the literal inline form, moving it back is a five-line change and loses the 10 tests.

**Ruling 2 — I did not split it from ruling 1.** They are one commit (`f2b5de9`), as instructed. The `validateSigningRelease` line is included because it cost one `matching {}` block and measurably flipped the order (see Checks); it produces no artifact and changes no signing behaviour.

**Ruling 3 — the tripwire throws at configuration time, in the convention plugin**, so it fires on *any* invocation of `:app` or `:domain` (proven on `:app:tasks`, not just on a gate task). The known-set includes the AGP-created test source sets (`androidTest*`, `screenshotTest*`, `testRelease`) so it cannot cry wolf; a new build type (`staging`) or any flavour source set (`free`, `freeDebug`) is unknown and fails the build with a message naming both lists and the decision each needs.

**Ruling 4 — why `check` and not a list of gate tasks.** The defect is that CI's gate was silently *narrower* than the Check command. Naming the four gates in the workflow fixes today's instance and rebuilds tomorrow's: R-2 is about to add `koverVerify` and a fuzz task to `check`, and neither would run on a PR. `check` is the Check command in `CLAUDE.md` and the studio's definition of done, so CI == check == done, permanently. I also added a second step for `./gradlew -p build-logic test`: `build-logic` is an **included** build, so its 54 tests — the contracts for the ad-ID, Play-Games-ID, signing and (now) gate-scope resolutions — are not part of the root `check` and have never run in CI either. That second step is my judgement call under ruling 4's delegation and can be dropped in one line if the auditor disagrees.

**The CI time cost, honestly.** `check` adds, over the old task list: the eight literal-gate tasks (sub-second), `:app:lint` (minutes), and `:domain:depthSweep`. The sweep is **~11 minutes locally** (the tech-lead's recorded figure; `domain/build.gradle.kts` sets `outputs.upToDateWhen { false }`, so it never runs up-to-date and the build cache cannot help it) and a 2-core GitHub-hosted runner is slower than this machine. **Estimate: +12–20 minutes per PR, not measured by me** — I did not run `check` or `depthSweep` because the producer owns that run and the machine was busy. Is it too high for a PR? My view: it is at the edge. A ~20-minute PR gate on a one-person studio merging a few branches a week is tolerable, and the alternative reopens the exact hole this task closes. If it proves too slow, the fix is to give `:domain:depthSweep` its own parallel job (wall clock becomes `max`, not `sum`) — that is a tech-lead/release-manager decision about tiers, and I did not take it.
