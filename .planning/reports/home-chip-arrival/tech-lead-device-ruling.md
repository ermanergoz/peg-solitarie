## 2. Ruling 2 — the boot deviation (D-2): accepted; the sitting of record stands
**What P-1.8 asks:** a cold boot for the sitting (`-no-snapshot-save`), then the launcher wait (Decision 1, P-1.8; fonts Ruling 2). It exists so a sitting starts from a known device state, with nothing carried in from a snapshot. Attempt 5 ran on the cold boot of 10:13:54, booted with `-no-snapshot-load -no-snapshot-save -no-boot-anim`, so that property held. What differs is that four attempts (10:44–≈12:55) came before it on the same boot. **Accepted, on these grounds:**
1. **The earlier activity was the sitting's own activity.** Installs, `compile -m speed -f`, force-stops and about 400 cold launches, all of the same two APKs. This is what any sitting does to the bench by its midpoint. It touched only this package's install, compile and data state, and it touched both arms alike.
2. **It cannot favour one arm.** The arms are interleaved in blocks of five, swapped only at block boundaries, and the first sample of each block is discarded. A slow drift in device state lands on both arms. Equal ART status held on every swap (`[status=verify]` on both), and all 20 swaps matched by sha.
3. **The guard measured that exact state.** Attempt 5's null control, run in the same attempt on the same boot, gives a floor of 6.0 ms (N1 402.0 ms, N2 396.0 ms), far inside the 150 ms VOID line. The distributions are tight: arm maxima 403 ms (A) and 410 ms (B), no outlier. The delta of 16.0 ms sits 84 ms under the 100 ms threshold. For the boot's age to flip the verdict, it would have to add more than 84 ms to one arm only, which point 2 rules out.
4. **The launcher wait was longer than required.** The launcher was idle from 12:53:53 to 13:05:57, more than Ruling 2's 3 minutes. The before-`uptime` was read fresh (2.31), and the after-`uptime` was 1.51.
5. **No outcome was selected.** Attempts 1, 2 and 4 were voided on precondition 3 by the timestamped host poll (`quiet-poll.log`, the first busy reading named per attempt). Attempt 3 was voided on its floor (183.5 ms). The rule that voided them was objective and did not depend on their numbers. Their numbers are not evidence and this ruling does not rest on them. I read them for one thing only: whether re-attempting hid an adverse result. It did not, because none computed a FAIL (`stats.txt`: deltas 14.0, 42.5, VOID, −338.0 ms).

**Forward rule for later sittings (candy-backdrop, any release sitting)**, to go into tech-design §10's 15e row with the mirror rows (brief Open issues 4):
> *Re-attempt on the same boot (2026-10-24, `home-chip-arrival/tech-lead-device-ruling.md` §2).* An attempt voided by a precondition may be re-attempted on the same cold boot. The cause must have been off the device: host load, a concurrent build, or an operator slip. It must not have been an event on the device, such as a crash, ANR or system dialog, a GMS or Play update, a foreign install or settings change, or `Data-Free` below 4 GB. Before the new attempt, the bench state is re-verified (installed sha256, ladder, settings), the launcher is idle ≥ 3 minutes, and the before-`uptime` is read again. The attempt runs its own null control, as every attempt does. The evidence names the boot time and the attempts that ran before it on that boot. A device-side cause, or any doubt about which kind of cause it was, requires a new cold boot.

## 3. Ruling 3 — the foreign APK on the reserved bench: effect and routing
**Facts, from files only:**
- **What QA found.** `bench-state-before.txt` shows the bench's installed `base.apk` sha256 as `dbe100e2bc11f0ca1f0a43bd8365abb9b7ceb7341d6fd85b4b17428f8f655589`. The app data was dated 2026-10-21 21:25, with 0 `level_result` rows and no save (`qa-engineer.md`, Summary and Open issue 3). The bench had been left after H-3 (2026-10-18) with phase 15's arm B and the seeded ladder (D-1 condition 3).
- **Whose APK it is.** The hash is the founder's GM6 install: 3.0.0, versionCode 3, "test-only debug sideload, same debug cert". Reinstalling it on the GM6 needed `-t`, because `-r -d` failed with TEST_ONLY (`hint-undecided/qa-engineer.md`, line 20 and Checks line 80).
- **The hint QA did not put it there.** That session pulled the APK on 2026-10-24, three days *after* the bench's data date, and records "`emulator-5554` (`Pixel_9a_bench`) was never touched".
- **What the TEST_ONLY flag suggests.** `android:testOnly` is set by an IDE Run (Android Studio injects it). A Gradle command-line build (`assembleDebug`, `installDebug`) does not set it. The evidence therefore points away from a studio agent's Gradle build and towards an IDE deploy that reached the running bench, a device left up at the default serial `emulator-5554`. This is a hypothesis, not a finding: who did it is the retro's to establish.

**Effect on this branch: none. No re-sit is owed for it.** The protocol caught the change through QA's pre-sitting state read, and QA re-established precondition 8 before attempt 1. The re-seed meant writing the ladder and preference with `seed.sh` and `setpref.py`, making one save by a real jump, and confirming Home in `seed-home.png` and `seed-home-relaunch.png`. Every swap's installed sha matched its arm, and the P-1.2 diff was clean. Whatever the foreign install did to the app's data, both arms and the null control ran on the state QA re-established, and that state is the same for every arm.

**Routing:**
- **R-3a — the producer, now (an instrument measure under the tech-lead's authority over the bench's use, 15v and D-1).** D-1 condition 3's "the producer *may* shut it down" becomes ***is* shut down between sessions**. A running bench at the default serial is what any IDE Run or any `adb` call that picks the first device can reach. The producer shuts it down now with the one command D-1 already allows it (`adb -s emulator-5554 emu kill`). The bench's data survives a shutdown, so C-2 and C-3 will find arm B and the ladder there. From now on the bench is booted only for a sitting or for its branch's device checks. The QA who booted it shuts it down as the last step of that session (C-8).
