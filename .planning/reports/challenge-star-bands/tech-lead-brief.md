### (b) The single Challenge cleared function

**Home and shape** — `domain/src/main/kotlin/com/app/pegsolitaire/domain/scoring/ChallengeClearRule.kt`:

```kotlin
sealed interface ChallengeFinish {
    data class Cleared(val stars: Int) : ChallengeFinish
    data object NotCleared : ChallengeFinish
}

object ChallengeClearRule {
    const val CLEAR_MAX_PEGS = 3                       // GDD R5, GD-SB-02
    const val PERFECT_STARS = ScoreParams.THREE_STARS  // the band is one star per peg: these coincide by design
    fun finish(pegsRemaining: Int): ChallengeFinish    // Cleared(CLEAR_MAX_PEGS + 1 - pegsRemaining) for 1..CLEAR_MAX_PEGS, else NotCleared
    fun isCleared(pegsRemaining: Int): Boolean         // finish(pegsRemaining) is Cleared
    fun status(board: Board): GameStatus               // Playing while !RulesEngine.isGameOver(board); Won when cleared; else Stuck
}
```

Rules of the object: it reads no `minimumPegs`, no footprint, no level, no mode (the count is absolute, GDD §6.1); a count below one — only a forged `Results` route can produce it — is `NotCleared`, never four stars; `scoring/` may depend on `rules/` for `status` (as `usecase/` already does), never the reverse. `ScoreCalculator.evaluate` gains a trailing `stars: Int = stars(pegsRemaining = pegsRemaining, minimumPegs = minimumPegs)` so every Classic caller is byte-identical and the Challenge caller passes `finish.stars`. A test pins `CLEAR_MAX_PEGS == PERFECT_STARS` the way `ScoreCalculatorTest` pins `THREE_STAR_MAX_PEGS == MINIMUM_PEGS_DEFAULT`: the GDD's "everything else derives" is true only while the two coincide.

**Who reads it, and where the mode branch is allowed** — exactly two `:app` sites, both of which already branch on mode:
1. `GameViewModel.statusFor(board)`: `activeChallengeLevel != null` → `ChallengeClearRule.status(board)`; Classic → today's `pegCount <= spec.minimumPegs`. `freezeAndFinishIfTerminal` passes `stars = (ChallengeClearRule.finish(pegsRemaining) as Cleared).stars` through a `when` (the status is `Won`, so the branch is exhaustive without `!!`); Classic passes nothing and keeps the default. `stuck` keeps deriving from the status, so it is true only at four or more pegs.
2. `ResultsUiState.isSolved`: `challengeLevel != null` → `ChallengeClearRule.isCleared(pegsRemaining)`; Classic → `pegsRemaining <= minimumPegs`. **`ResultsViewModel.isSolved` becomes a read of `_uiState.value.isSolved`** (build the state first, then derive the tier and the gate from it): today the ViewModel holds a second copy of the expression, and the CR-01 lesson is one test, not two equal ones. `tierFor` adds `CLEARED` — `challengeLevel != null && !isSolved → STUCK; stars >= 3 → PERFECT; stars == 2 → SOLVED; challengeLevel != null → CLEARED; else → STUCK` — and `isInterstitialEligible` stays `tier != STUCK`, so a one-star clear is eligible (GD-SB-16). The `Results` route keeps its `minimumPegs` arg (Classic needs it); T-10-06 (a trusted `stars` arg) stays accepted as recorded.

**The DAO** cannot call Kotlin, so it reads the same constant the way it reads the speed limit: `PlaySessionDao.flags` adds `AND stars = :perfectStars` to the hint-free, undo-free and speed `EXISTS` predicates, and `ProgressRepository` binds `ChallengeClearRule.PERFECT_STARS` beside `AchievementThresholds.SPEED_SOLVE_MAX_ELAPSED_MS`. A new predicate over the existing `stars` column: no schema change, `DB_VERSION` stays 2 (tech-design §4.1). Classic rows are always three stars (R4), so Classic is unchanged by construction.

**`GameStatus.Won` is not renamed.** The name is read by dozens of files and tests and means "terminal and past the finish test"; its KDoc is corrected to say so (Classic `pegCount <= minimumPegs`, Challenge `ChallengeClearRule`). `Stuck`'s KDoc likewise ("more pegs than the mode's finish admits").

**Resume and hint claims (GDD §12.3(3)), confirmed with one correction and one code change.** `SnapshotMapper.fromDto` never reads `generatorVersion` and `applyRestored` installs the stored initial board and history, so a snapshot stamped 1 resumes on its board with undo and elapsed time intact. Its hint reaches the solver — but not through the legality guard the GDD names: on every resume `solution` stays `null` and `onRecordedLine` is `false` (`GameViewModel.applyRestored`), so the recorded line is never consulted; same outcome, different mechanism (finding F-1). **Restart is not free:** `resetToInitial` rebuilds from the stored `initialBoard`, so a restarted old-stamp level would deal the v1 board for ever, and CLC-06 / SB-Q9 ("Restart serves a different board") would fail. Ruled: `GameViewModel` keeps the restored stamp's `generatorVersion`; a Challenge restart whose stamp is not `GeneratorConstants.GENERATOR_VERSION` does the reset bookkeeping, clears the snapshot and then takes `loadChallengeBoardIfNeeded()` — the existing off-main-thread generation path, which also installs the level's recorded line — instead of the in-place rebuild; a current-stamp or fresh game keeps today's regeneration-free restart (D-06). One more I5 hole on the resume path: `SnapshotMapper.resolveMinimumPegsOrNull` case 2 ("absent target, footprint in the catalog → the catalog floor") would hand a Challenge blob on the Diamond-41 footprint a floor of 2; it is keyed on `dto.mode` (Challenge → `MINIMUM_PEGS_DEFAULT`; only a Classic blob consults `CLASSIC_SPECS`). No such blob exists today, so this is I5 made true, not a data fix.

### (c) How pool specs carry `minimumPegs = 1`

`DifficultyTiers.CanonicalFootprints.ORDERED_BY_SIZE` becomes `Boards.CLASSIC_SPECS.map { BoardSpec(inPlay = it.inPlay, target = it.target, minimumPegs = BoardConstants.MINIMUM_PEGS_DEFAULT) }` — a footprint copy for **every** entry, uniformly, never a Diamond-41 special case, so the invariant holds by construction for any board the catalog gains later. `target` is kept: `lastPegOnTarget` and the canvas read it today, and the four cross copies are then content-identical to the catalog specs (the `CENTER_FINISH` predicate filters `mode = classic`, so a Challenge level on the English-33 footprint cannot earn it). Consequence for tests: a generated spec is no longer the catalog instance and `BoardSpec` has no `equals`, so `DifficultyTierTest` and `FreeformValidityTest`, which ask `spec in canonicalSpecs`, compare `spec.footprint` against `Boards.CLASSIC_SPECS.map { it.footprint }` instead. Rejected: a `copy`-style helper on `BoardSpec` (it is not a data class, and the one call site does not justify API), and making `BoardSpec.minimumPegs` a generator-side override (the floor is a property of the spec the board carries into every consumer — solver, resume blob, Results).

The assist side is safe without a change: `OpeningBook.lookup` is keyed by footprint, so a Challenge board on a cross footprint that happens to be a book position gets a move on a proven one-peg line, which is correct; a Challenge board on the Diamond-41 footprint can never be a Diamond book position, because every Diamond book entry is reachable from the centre start, whose GF(4) class admits no one-peg position, while every generated board was built backwards from one. The solver's goal is the spec's `minimumPegs`, one on every Challenge board by I5, so the Pagoda prune keeps its full one-peg strength on that footprint.
