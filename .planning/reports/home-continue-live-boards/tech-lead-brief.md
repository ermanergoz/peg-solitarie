## Rulings

### Ruling 1 — a snapshot that will not rebuild is withheld and purged (Open issue 1)

**Decision.** In `HomeViewModel`'s Classic branch, after the catalogue check, when `SnapshotMapper.fromDto(dto, rulesEngine)` returns `null`, the chip is **withheld** and the row **purged** (`progressRepository.clearSnapshot(MODE_CLASSIC)`), exactly as `resumableClassicBoard` already does for an unknown id (CR-01). The spec's "shows the play arrow and nothing else changes" for this case (§4.2.7, "When the position cannot be rebuilt") is struck.

**Why.**
- *The resume path's own behaviour.* `GameViewModel.kt:546-561`: on Continue it loads the snapshot, calls the same `fromDto`, and on `null` with a non-null DTO it **clears the row and loads a fresh board** ("purge the row (WR-02) so the Continue affordance disappears instead of forever restarting a fresh board"). A Home chip for such a snapshot is therefore the phantom WR-02 defines, with the row's purge deferred to the tap: it promises a saved game and starts a new one. Showing it with an arrow would be Home contradicting the screen it navigates to.
- *Consistency.* The three unusable shapes are now handled by the same rule in the same place: a blob that does not decode (the repository purges on load, WR-02, `ProgressRepository.kt:679-693`); a blob whose id the catalogue does not know (Home withholds and purges, CR-01, `HomeViewModel.kt:255-265`); a blob whose history does not replay (this ruling). `GameViewModelResumeTest.aTamperedSnapshotFallsBackToTheNormalLoadInsteadOfCrashing` already pins the resume path's purge; Home's rule becomes its mirror, and `HomeViewModelTest.aClassicSnapshotOnAnUnknownBoardOffersNoContinueAndPurgesTheRow` its template.
- *The oracles and the cloud-save tests are untouched.* Oracle 3 (§4.2.1) is the chip's presence, title, supporting line and target **for a save the game wrote**. Every snapshot `GameViewModel` writes replays by construction: `toDto` takes the initial board and a history whose every move was applied through `RulesEngine.applyMove` after a `legalMoves` check, and `fromDto` re-checks it with the same engine. `11-HUMAN-UAT.md` tests 10, 11 and 13 read genuine saves (test 11's D-04 sub-check is a Challenge game, which this branch does not touch); and the in-progress snapshot never leaves the device (tech design §5.7), so no cloud event — restore, merge, replace — can produce a non-replaying Classic blob. `SnapshotMapperTest` and `ResumeRepositoryTest` test the codec and the repository and are unaffected. A non-replaying blob exists only through tampering or corruption, which is exactly the population CR-01 already withholds.
- *Cost.* One branch in `resumableClassicBoard`, one `HomeViewModelTest` case, and a fix to the test fake (Handoff C1: today's fake builds a hollow DTO that the codec rejects — see there). No repository member, no schema, no double touched. The purge is best-effort, as CR-01's is; a failed clear leaves the row for the next emission.
- *What this does to the Classic chip's arrow.* In production the Classic chip now always has a board: `classicResumeBoard` is non-null whenever `classicResumeLevelId` is (an invariant the ViewModel test pins, Handoff C1 c). `ResumeTile`'s `board == null` branch stays, because the Challenge chip uses it and because §6.5's degradation step 2 ("the thumbnail reverts to the play arrow and the position is not rebuilt") is a one-line fallback through it if a 15e sitting ever forces it — under that step, and only then, the presence rule returns to decode + catalogue id.

### Ruling 2 — how `HomeViewModel` gets the rules and the replay runs (Open issue 1, second half)

**Decision.**
- `HomeViewModel`'s constructor gains `private val rulesEngine: RulesEngine` and `private val defaultDispatcher: CoroutineDispatcher`. Both bindings exist: `DomainModule.provideRulesEngine()` (the `:domain` object, `@Singleton`) and `DomainModule.provideDefaultDispatcher()` (the **unqualified** `CoroutineDispatcher` = `Dispatchers.Default`), the same two `GameViewModel` injects (`GameViewModel.kt:115,122`). **No new `@Provides`, no qualifier, no module edit; `:domain` is not touched** (`RulesEngine` carries no Hilt annotation; `SnapshotMapper` is `:app/data/resume`, and `ui/` → `data/` + `:domain` is §2.3's permitted direction). `@IoDispatcher` is not used: the replay is CPU, not I/O.
- The replay runs **under `withContext(defaultDispatcher)`** inside `resumableClassicBoard`, after the suspending `loadSnapshot` and after the catalogue check, in the resume-modes collector — one hop, the same shape as the resume path's `withContext(defaultDispatcher)` for its CPU work (`GameViewModel.kt:578`). Not inline on Main, for two reasons: rules/kotlin-android.md's "dispatchers injected" is also "CPU off the main thread on a start destination", and the replay's cost is bounded by the board only for *legal* histories (`replayOrNull` stops at the first illegal move; at most `initialPegs − 1` applications) while `toMoveHistoryOrNull` maps **every** stored tuple, whose count the codec bounds only by what Room read — a hop makes Home's main thread independent of the blob's size. Structurally it never runs on the first frame: the collector resumes only after the Room read, and the chip's room opens on the emission (D-03n), so 15x's "`BoardCanvas` on Home at most once" and §6.5's first-frame rule hold without a special case.
- Order inside `resumableClassicBoard` (it returns a private `ClassicResumable(levelId: String, board: Board)?`, replacing today's `ClassicLevelDescriptor?`): `loadSnapshot(MODE_CLASSIC)` → `null` returns `null` (the repository purged an undecodable row); catalogue lookup by `dto.levelId` → `null` clears and returns `null` (CR-01, as today); `withContext(defaultDispatcher) { SnapshotMapper.fromDto(dto, rulesEngine) }` → `null` clears and returns `null` (ruling 1); else `ClassicResumable(descriptor.id, restored.currentBoard)`. The state update sets `classicResumeLevelId` and `classicResumeBoard` from it, **both or neither**. `previewBoard` is no longer read by Home; the KDoc at `HomeViewModel.kt:242-254` (returning the descriptor "because the catalogue lookup already has the board in hand") is rewritten: the board now comes from the codec; the catalogue is still read once, for the id (QUAL-01 holds — the screen still never maps an id to a board).
- Test seam: `HomeViewModelTest.viewModelFor` and `HomeViewModelCloudTest`'s factory pass `RulesEngine` and their `testDispatcher` as `defaultDispatcher`; `runCurrent()` drives the hop under `runTest(testDispatcher)` as it does today. No Turbine change.
- Field names in `HomeUiState` are **unchanged** (`classicResumeLevelId`, `classicResumeBoard`), so §13's "`HomeScreenTest` and fixture states … pass unedited" holds; `classicResumeBoard`'s KDoc is rewritten to the saved position and the invariant. A single `classicResume: ClassicResume?` value was considered and not taken: structurally better, but it touches every fixture in `HomeScreenTest`, `HomeLayoutTest`, `HomeChipArrivalTest`, `BackdropPixelTests` and the previews for an invariant one ViewModel test pins.
