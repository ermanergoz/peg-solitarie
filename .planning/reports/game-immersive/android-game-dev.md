## Deviations — routed through the producer
1. **§3.8 (d) fails below API 30 as written; fixed inside the one source. Tech-lead to rule.** On API 27 the first post-fix build put gameplay's strip at y ≈ 0 and the dock into the navigation band. Two throwaway probe builds (never committed) logged Compose's values while entering gameplay. `systemBarsIgnoringVisibility` went `63/126 → 62/0 → 14/0 → 0/0` px as the bars hid, and back on Home only to `63/0`, so after one round trip every screen would also lose its bottom inset. Meanwhile `ViewCompat.getRootWindowInsets(view).getInsetsIgnoringVisibility(systemBars())` held `top=63, bottom=126` throughout, and `dumpsys window` showed `stable=[0,63][0,126]`. Cause: below API 30 androidx emulates the bars' slide for the Compose host, and Compose's `InsetsListener.onProgress` writes the emulation's interpolated insets into its "ignoring visibility" values; those insets carry no stable value. From API 30 the platform drives the animation, and API 31 was correct. The fix: `stableSystem` keeps its name, meaning and call sites. From API 30 it is the ruled `systemBarsIgnoringVisibility ∪ displayCutout`; below 30 it is `RootStableSystemInsets`, the root's stable bars ∪ cutout, re-read whenever the host's visible insets are dispatched (it reads them only to subscribe). Costs: a few small allocations per layout pass below API 30; the below-30 branch selection itself runs only on a device, because Robolectric here runs sdk 34 alone, so its class is tested with the root read injected. **Consequence for QA:** an API ≤ 29 image belongs in 30g, 30i and 30r (the founder's phone is "Android 14 or older"); `Pixel` (API 27) is on this machine.
2. **The source gate's scope.** The brief's literal "a bare `systemBars`" would flag the seam's own `WindowInsetsCompat.Type.systemBars()` mask that §3.8 (a) requires. The gate therefore matches Compose's inset reads (`safeDrawing`, `safeContent`, `safeGestures`, `statusBars`, `navigationBars`, a bare `systemBars`, their `Padding` forms and the per-bar stable forms), excludes anything preceded by `Type.`, and the seam's locals are named `seam`. It also checks more than the brief asks: each `TopAppBar` must pass exactly `stableSystem.only(Horizontal + Top)`, `ExperimentalLayoutApi` may be named only in the source, and neither M3 visible default may be named anywhere. For the code-auditor.
3. **Images.** P0 and the post-fix reads used API 27 and 31, not 30 and 34 (above). For the producer: QA's 30i/30r ask for API 30 and API 34 images, which need a disk-space decision. The temporary API 31 AVD was deleted; its recipe is `.planning/qa/game-immersive/api31_immersive_p0-config.ini` (put it at `~/.android/avd/<name>.avd/config.ini` with a matching `<name>.ini`; 611 MB once booted).
4. **For the ux-designer (no spec line covers it):** on API 27 and API 31, the first time the app hides its bars after install, SystemUI shows its one-time "Viewing full screen — To exit, swipe down from the top. GOT IT" panel over the top of the screen with a dim (`post/final-api27-first-immersive-entry-system-confirmation.png`). The platform owns it, it persists per package, and no public API suppresses it. QA should tap GOT IT before reading 30g–30n on such images; §6.2 may want a line.
