## 1. The seam — where the policy lives, how it is tested, the re-assert, the dialogs (§3.8 (a)–(c))

**The seam** (`ui/window/SystemBars.kt`). `enum class SystemBarsState { Shown, Hidden }`: Hidden means both bars hidden with `WindowInsetsControllerCompat.BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE`, Shown means both shown with `BEHAVIOR_DEFAULT` (core 1.18.0, `WindowInsetsControllerCompat.java:79,104`). `interface SystemBars { fun apply(window: Window, state: SystemBarsState) }`, idempotent. The production object `WindowInsetsSystemBars` builds `WindowInsetsControllerCompat(window, window.decorView)` (the constructor, never the deprecated `ViewCompat.getWindowInsetsController`, which `allWarningsAsErrors` would reject), sets the behaviour, then `hide(Type.systemBars())` or `show(Type.systemBars())`. The compat object carries the policy to every API level (`SYSTEM_UI_FLAG`s below 30, immersive-sticky for the transient behaviour). `LocalSystemBars` is a `staticCompositionLocalOf<SystemBars>` whose default is a no-op object (`LocalSoundPlayer`'s idiom, `audio/LocalSoundPlayer.kt:21`): `MainActivity` provides `WindowInsetsSystemBars` inside its existing `CompositionLocalProvider`, tests provide a recording fake, previews get the no-op. **The seam takes a `Window`, never an `Activity`**: `PlatformBoundaryRules.uiAndDomainNeverTouchAnActivity` forbids `android.app.Activity` in `..ui..`, and `LocalActivity` is the example its KDoc names. It is not `platform/`: a framework type with no SDK and no Activity (§2.4, "What is *not* platform", the audio precedent).

**The policy** (`navigation/SystemBarsDestinations.kt`). `fun NavDestination?.systemBarsState(): SystemBarsState = when { this?.hasRoute<Gameplay>() == true -> Hidden; this?.hasRoute<Results>() == true -> Hidden; else -> Shown }` — the exact shape of `backdropDensity()` in the same package (the backdrop's R1). The `else` is the "scoped constant with an `else` branch" D-05g asks for: no call site names a state, and a destination added later shows its bars. Its adapter `NavSystemBars(navController, hostWindow: Window?, barsState: MutableState<SystemBarsState>)` is composed **after** the `NavHost` in the same `Box`, beside `NavBackdrop`, for the same reason that one is: the `NavHost` sets its graph and restores a saved back stack during its own composition, so the synchronous `currentBackStackEntry` read gives the right state on frame 1 (BD-06's restore case: a stack whose top is `Gameplay` is `Hidden` on its first frame, 30a). It reads the committed entry (`currentBackStackEntryFlow` collected with `initial = currentBackStackEntry`), writes `barsState.value`, and in a `SideEffect` calls `LocalSystemBars.current.apply(hostWindow, state)` — composition apply runs before the frame's layout and draw, which is 30a's "before its first draw". The host window is a new parameter, `AppNavHost(hostWindow: Window? = null, …)`, passed by `MainActivity` as `window`; `null` (previews, `NavFlowTest`, `BackdropSettleTest`'s stand-ins) applies nothing and keeps the state current. It follows the host's defaulted-slot style, so detekt's thresholds, which already accept the thirteen defaulted slots, are unchanged.

**The state for the dialogs.** `LocalSystemBarsState` is a `staticCompositionLocalOf<State<SystemBarsState>>` the host provides above the `NavHost` with the `MutableState` it owns (`remember { mutableStateOf(SystemBarsState.Shown) }`) — the `State` itself, not its value, the `LocalBackdropSceneReady` idiom (tech design §3.5 R3) — so a navigation recomposes the adapter and the readers that call `.value`, never the host's body (R1).

**Re-asserted on resume** (30b). In `NavSystemBars`, `LifecycleResumeEffect(state, hostWindow) { apply; onPauseOrDispose { } }` (lifecycle-runtime-compose 2.9.4, `LifecycleEffect.kt:444`) on the composition's `LocalLifecycleOwner` — the activity's, because the adapter sits outside the `NavHost`'s per-entry content. It re-applies the current state on every `ON_RESUME`: after a rewarded or interstitial ad (the SDK's own activity pauses ours and returns), a Play Games UI, the launcher, the lock screen, the shade. On Home it re-applies `Shown`, which the fake records as no `Hidden`. Rejected: `AppForegroundTracker` (`ProcessLifecycleOwner` deliberately does not fire for a same-process activity's return — its KDoc's own argument); a hook on `DefaultForegroundActivityProvider` (reachable only from `platform/`, by ArchUnit); an `onResume` override in `MainActivity` (zero JVM-test exposure by construction, while the effect is driven in a test by a `LifecycleRegistry` owner exactly as `BackdropSettleTest.TestLifecycleOwner` does).

**Dialogs mirror the state** (30c). `ui/window/MirrorSystemBars.kt`: a composable placed first inside each dialog's content — `RestartConfirmDialog` (the M3 `AlertDialog`, in its `title` slot), `AdOfferDialog`, `PlayGamesPromptDialog`, `ProfileSwapDialog`. It reads the dialog's own window through `LocalView.current.parent as? DialogWindowProvider` (`DialogLayout` implements it: ui 1.11.3, `AndroidDialog.android.kt:294-300`) and `LocalSystemBarsState.current.value`, and in a `SideEffect` keyed by `remember(window, state)` applies the state through `LocalSystemBars` to that window; nothing on dispose, so closing records no `Shown`. The two Home dialogs open only on Home today (`HomeScreen.kt:184`, `:204`); they carry the mirror anyway, for the rule's uniformity (applying `Shown` there is a no-op), so a dialog added later to gameplay mirrors by construction. `DialogProperties` are unchanged (`decorFitsSystemWindows` defaults true in ui 1.11.3). **Pre-ruled fallback, inside the review loop, never a new ruling:** if 30l's recording shows a dialog's surface re-centre between its first and second frame — its decor fits the system windows, so a hidden bar enlarges its frame by the bars' extents — that dialog takes `decorFitsSystemWindows = false` with its content checked at the same position; a bar appearing is never accepted. In-composition surfaces (the rescue banner, the Undecided notice, the snackbar, the Results ad scrim) need nothing; the app has no `Popup` or `DropdownMenu` (grep, 2026-11-01).

**How it is tested in Robolectric.** A fake `SystemBars` records `(window, state)` pairs; the tests observe the fake, never the platform:

Home composed → the first record is `Shown`; navigate to Gameplay → `Hidden`; to Results → `Hidden`; Results → Home → `Shown`; a restored stack with `Gameplay` on top (`StateRestorationTester`, as the backdrop's BD-06 test) → the first record is `Hidden`; a stub destination registered by the test → `Shown`. Red: with `NavSystemBars` not composed the fake records nothing.
- 30b `SystemBarsResumeTest`: `CompositionLocalProvider(LocalLifecycleOwner provides <LifecycleRegistry owner>)`; at Gameplay, RESUMED → STARTED → RESUMED records a new `Hidden`; at Home the same cycle records no `Hidden`.
- 30c `DialogMirrorTest` (`ui/window/`): `GameScreen` fixtures with `confirmRestart = true` and with a `pendingAdOffer` (idle and loading), under `LocalSystemBarsState provides mutableStateOf(Hidden)` and the fake → a record whose window is not the host's, state `Hidden`; close → no `Shown`. The two Home dialogs under `Shown` → `Shown` for their window. Red: the mirror removed → no record for the dialog window.
- The production object: `WindowInsetsSystemBarsTest`, Robolectric sdk 34 on a `ComponentActivity` window — after `apply(Hidden)`, `WindowInsetsControllerCompat(window, decor).systemBarsBehavior == BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE`; after `apply(Shown)`, `BEHAVIOR_DEFAULT`. If Robolectric's controller cannot read the behaviour back at sdk 34, the test asserts what it can and the report says so; the bars' visibility is the device's (30g–30n).

## 2. The shared stable-inset source and the F-33 deviation (§3.8 (d))

`ui/window/StableInsets.kt`: one `@Composable` getter, `val WindowInsets.Companion.stableSystem: WindowInsets get() = systemBarsIgnoringVisibility.union(displayCutout)`. `systemBarsIgnoringVisibility` is `@ExperimentalLayoutApi` in foundation-layout 1.11.3 (`WindowInsets.android.kt:265`; `displayCutout`, `safeDrawing` and `union` are stable), so the one `@OptIn(ExperimentalLayoutApi::class)` in `app/src/main` sits on this getter — an opt-in, not a suppression under §9.8. Call sites: every `Scaffold` (`HomeScreen`, `GameScreen`, `ResultsScreen`, `ClassicCatalogScreen`, `SettingsScreen`, `LicensesScreen`, `GoogleNoticesScreen`, `LicenseTextScreen`, `GoogleNoticeTextScreen`) passes `contentWindowInsets = WindowInsets.stableSystem`; every `TopAppBar` (`ClassicCatalogScreen`, `ResultsScreen`, `SettingsScreen`, `LicensesTopBar`) passes `windowInsets = WindowInsets.stableSystem.only(WindowInsetsSides.Horizontal + WindowInsetsSides.Top)` — today's default `TopAppBarDefaults.windowInsets` is a visible read, and a Results top bar left on it would lose its 24dp the moment the bar hid (30d's red); `TutorialScreen`'s column takes `.windowInsetsPadding(WindowInsets.stableSystem)` for `.safeDrawingPadding()`, its explanatory comment rewritten to say so. No screen has a text field, so no IME is unioned (D-05g's "where a screen has one" is empty today). `GameStatusStrip.kt:70` and `GameActionDock.kt:64` mention the old modifiers in history comments only; they stay.

**Why the per-screen place and not the host once.** F-33's "once in the host" would zero nine `Scaffold`s and four `TopAppBar`s and pad the `NavHost` — the same number of touch points, a bigger behavioural change from the D-05d form that 18b/18c measure, and it re-opens the geometry the tech design keeps for 3.0.0 (§3.5, §14.2). The per-screen form with one source is the smaller change and the idiomatic place to hand M3 an inset value.

**Held by two things.** (1) `StableInsetsSourceTest` (JVM, the `WindowThemeApi35FilesTest` shape): over every `.kt` under `app/src/main/java` with `//` and block-comment lines stripped, no file but the source names `safeDrawing`, `safeContent`, `safeGestures`, `statusBars`, `navigationBars`, a bare `systemBars` (not followed by `IgnoringVisibility`), `ScaffoldDefaults.contentWindowInsets`, `TopAppBarDefaults.windowInsets` or the `*Padding()` modifiers of those; and in every file the count of `Scaffold(` equals the count of `contentWindowInsets =`, and `TopAppBar(` of `windowInsets =`. (2) The behavioural proof, 30d–30f (below). Below API 30 the compat `getInsetsIgnoringVisibility(systemBars())` is the platform's `getStableInsets()`, which the `LAYOUT_STABLE | LAYOUT_FULLSCREEN | LAYOUT_HIDE_NAVIGATION` flags of `setDecorFitsSystemWindows(false)` define — so §2 and §3 hold together: without the edge-to-edge call the stable read below 30 is not the bars' heights.

**rules/compose.md F-33, the deviation.** The rule: "edge to edge, the navigation host pads off the system bars once, with `Modifier.safeDrawingPadding()` (F-33); a UI test holds both in dark mode." This product deviates in two halves, both **approved at product level, a tech-lead decision** (tech design §3.5, §3.8 (d), §14.2, §17): the *source* — D-05g needs the stable insets everywhere, because a screen that read `safeDrawing` would be laid out at zero while the bars are hidden on the way back from gameplay and jump by the bar's height as they slide in; and the *place* — each screen once, as built since D-05d (phase 15) and recorded in §3.5. F-33's intent — each bar applied exactly once, nothing under a bar, edge to edge — holds and is tested (18b, 18c, 30d–30f; the dark-mode half by `TransparentContainersTest` and BD-09). The place half stays a §14.2 item under its own condition. **Lesson candidate for the retro** (the ux-designer's Open issue 3, seconded): an edge-to-edge app that hides a bar on any screen pads off the stable insets everywhere, or its other screens jump; `safeDrawing` is the wrong default for such an app.

## 3. Below-API-35 edge to edge, F-2, and which grey-tint candidate is real (§3.8 (e)–(f))

**The mechanism: `enableEdgeToEdge()`, the theme untouched.** `MainActivity.onCreate` calls `enableEdgeToEdge()` before `super.onCreate()` (androidx's documented order; it touches no injected field), with its defaults — read from the pinned activity 1.13.0 source, `EdgeToEdge.kt:80-81`: `statusBarStyle = SystemBarStyle.auto(Color.TRANSPARENT, Color.TRANSPARENT)`, `navigationBarStyle = SystemBarStyle.auto(DefaultLightScrim #e6ffffff, DefaultDarkScrim #801b1b1b)`. No argument is passed. What it does per API level (`EdgeToEdge.kt`, the impl chosen at `:86-100`, the cutout adjusted at `:128`):

| API | Impl | Status bar | Navigation bar | Cutout mode |
|---|---|---|---|---|
| 24–25 | `EdgeToEdgeApi23` | transparent; light-icons flag = `!isDark` | the dark scrim `#801b1b1b`, light buttons | none (no cutout API) |
| 26–27 | `EdgeToEdgeApi26` | transparent; `!isDark` | `#e6ffffff` under dark buttons in light, `#801b1b1b` under light buttons in dark | none |
| 28 | `EdgeToEdgeApi28` | as 26 | as 26 | `SHORT_EDGES` |
| 29 | `EdgeToEdgeApi29` | transparent (`auto` → transparent); `isStatusBarContrastEnforced = false` | transparent; `isNavigationBarContrastEnforced = true` (the platform's scrim for three-button) | `SHORT_EDGES` |
| 30–34 | `EdgeToEdgeApi30` | as 29 | as 29 | `ALWAYS` |
| 35–36 | `EdgeToEdgeApi35` | transparent (no effect on 35+) | transparent; no `ProtectionLayout` is added, since both styles resolve transparent; contrast enforced true | `ALWAYS` |

On 35+ the call restates the v35 theme pair's values at run time (`isAppearanceLightStatusBars/NavigationBars = !isDark`, transparent, contrast enforced) and nothing a player sees changes; the bench's criterion 29 (2) re-run (30t) is the proof. `setDecorFitsSystemWindows(false)` is what makes the bands the backdrop's below 35 and what D-05g part 5 means by "the window goes edge to edge". The cutout mode D-05g asks for below 35 — "the short-edges cutout mode or its equal, or the platform letterboxes the cutout in black the moment the bar hides" — is the call's: short edges on 28–29, always on 30+; before 28 there is no cutout. The call also adds one GONE, non-drawing listener `View` to the decor that re-runs the set-up on a configuration change: the whole first-frame cost, which the 15e sitting measures.

**The theme files, the two tests, and F-2.** `res/values*/themes.xml` keep their items; `WindowThemeTest` and `WindowThemeApi35FilesTest` pass unchanged — `docs/ux-spec.md` §13's row: "if it is an activity call, nothing here changes and 30r is the device read". Three comments that say the window is not edge to edge below 35 (`WindowThemeTest`'s class KDoc, `values-v35/themes.xml`'s and `values-night-v35/themes.xml`'s comments) each gain a dated one-sentence correction — text only; `WindowThemeApi35FilesTest` parses items, not comments. **F-2 (the status-bar icon contrast rule) still holds:** the window theme's `windowLightStatusBar` owns the first frame and the system's starting window; the call sets the identical flag (`isAppearanceLightStatusBars = !statusBarIsDark`) from the identical source (`detectDarkMode` reads `Configuration.uiMode`, as `isSystemInDarkTheme()` does), so the theme and the call cannot disagree in either mode; on gameplay and Results the bar is hidden, and while it shows transiently its icons keep that appearance over the platform's own translucent overlay. **Criterion 29's below-35 read** takes its second admitted form everywhere below 35 — edge to edge under a scrim (androidx's on 26–28, the platform's on 29–34) with buttons ≥ 3:1 — and 24–25 get the dark scrim with light buttons; the developer records which form each image shows (29's 2026-11-01 note). Nothing sets `isNavigationBarContrastEnforced` to false (B-09/§5.5): the call sets it **true**.

**Rejected.** A theme-only route: no theme attribute turns `decorFitsSystemWindows` off, and `android:windowTranslucentStatus` forces a scrim of its own. Per-API `values-vNN` theme pairs for `statusBarColor`: five more whole-style restatements for a value the call sets in one line, and still no edge to edge. `WindowCompat.setDecorFitsSystemWindows` by hand plus manual colours and cutout modes: a re-implementation of the androidx function with the same per-API branches and `NewApi` guards to get right.
