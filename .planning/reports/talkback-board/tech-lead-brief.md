## Summary
- **The architecture:** real Compose semantics nodes, one per in-play cell, laid out by the same `BoardGeometry` that draws and hit-tests the board, in a pointer-less overlay inside `BoardCanvas` that exists only when `interactive = true`. The board stop sits on the host's slab. The drawing path, the tap path and the read-only Home path are byte-identical. No `AccessibilityNodeProvider`, no `AndroidView`, no `announceForAccessibility`.
- **The words** come from a pure JVM model (`BoardSpeech`) over `board`, `selected`, `legalTargets`, the hint pair and the last move; the strings are §8's 29 + 2, named exactly, with 1-based numbers applied in one place. The solver is never an input (TB-12, ArchUnit-pinned).
- **Every announcement** is one polite live region per board, the node the audio branch already made one, fed by one announcer that replaces audio's wrong-tap-only channel. Two ViewModel fields are added (`restartTick`, `undoneMove`); everything else is derived from state the boards already carry.

## 1. Findings for the D-TB checker — where the contract and this architecture meet
Each finding names a line of D-TB, what the pinned stack can do about it, what this brief builds, and what the checker is asked to confirm or amend. None is silently resolved in code.

**F-TB-1 — The focus table asks for four programmatic accessibility-focus moves; Compose BOM 2026.06.00 has no public API for one.** §11.1's table moves focus to (i) the destination cell after a jump by action, (ii) the new board's board stop when a tutorial step installs, (iii) the board stop after Undo or Restart from the rescue banner, and (iv) `onboarding_got_it` on completion. Every other row ("the cell activated", "that dock control") is free: a node TalkBack has focused keeps its focus while it exists, and this architecture keeps every cell node alive across state changes (§6). The four moves are not free. TalkBack cannot be told where to put accessibility focus; the one public lever is **input focus**: the target carries `Modifier.focusable()`, a `FocusRequester` requests it, Compose emits `TYPE_VIEW_FOCUSED`, and TalkBack moves accessibility focus to follow. This brief builds that (§6). ## 2. The semantics architecture
**Decision.** Per-cell **real Compose layout nodes with semantics**, in a `Layout` overlay inside `BoardCanvas`, composed only when `interactive = true`. The board stop is a semantics modifier on the host's slab. Rejected: a custom accessibility node provider (`ExploreByTouchHelper` on an `AndroidView` over the canvas). It would put the cells outside the Compose semantics tree, where `createComposeRule` cannot see them and TB-1 to TB-6 could not be JVM-tested; it would add a second hit-test path beside `BoardGeometry.positionAt`; and rules/compose.md's accessibility list is written for Compose semantics. Real nodes cost one layout pass over 33–45 children, which is nothing against the canvas draw.

**The tree, interactive (`BoardCanvas.kt`).**

    Box(modifier.aspectRatio(BoardMetrics.BOARD_ASPECT_RATIO))        // the caller's modifier lands here: the host's padding. (Amendment 1, A1.3: NOT the live region — that stays on the Canvas, below)
      Canvas(Modifier.matchParentSize().testTag(BOARD_CANVAS_TEST_TAG)
                     .onSizeChanged { canvasSize = it.toSize() }
                     .pointerInput(geometry) { detectTapGestures { … onCellTap } }
                     .boardAnnouncement(announcement))                 // today's chain, unchanged but for aspectRatio moving to the Box; the live region from the new `announcement: String?` parameter (Amendment 1, A1.3)
      BoardCellOverlay(spec, speech, onCellTap, Modifier.matchParentSize().testTag(BOARD_CELLS_TEST_TAG))   // after the Canvas, so it is above it for accessibility hit-testing

- The Canvas keeps its tag, its `onSizeChanged` and its `pointerInput`; `drawBoard` and everything below it are untouched. `GameFlowTest.tapCell` and `TutorialScreenTest.tapCell` click `BOARD_CANVAS_TEST_TAG` by percent offset; the Canvas fills the Box, so its bounds are what they were.
- The overlay carries **no `pointerInput`, no `clickable`, no `toggleable`**. Pointer hit-testing visits only nodes with pointer-input modifiers, so a finger tap passes through to the Canvas; TB-11's pass-through test proves it.
- **Read-only boards get today's tree, not a wrapped one.** `BoardCanvas` branches at the top: `if (!interactive)` composes exactly the Canvas it composes today, with today's modifier chain, and nothing else. This is what keeps Home's first frame (`HomeStage.kt:103`, `HomeBoardArt.kt:48`, both `interactive = false`) byte-identical in composition (§12). The code-auditor reads that every new `remember`, `Layout`, `semantics` and `focusable` sits under the interactive branch.

**The overlay (`BoardCellOverlay.kt`).** A `Layout` whose measure policy builds `BoardGeometry.forCanvas(spec, Size(constraints.maxWidth.toFloat(), constraints.maxHeight.toFloat()))` and places one child per cell, `cellSize` square, centred on `geometry.center(position)`. The geometry is computed **in measure from the constraints**, never read from the Canvas's `onSizeChanged` state: that state is one frame behind, and TalkBack caches bounds, so a cell reported from a stale size is found at the wrong place by explore-by-touch. The overlay and the Canvas are both `matchParentSize`, so the two geometries are the same object's arithmetic over the same size. `BoardGeometry.kt` is not edited; it already exposes `center` and `cellSize`.

The children are `spec.inPlay` sorted by `(row, col)` — `inPlay`'s own order is not relied on — each under `key(position)`, each a `Box` with:

    Modifier

            contentDescription = cellText                 // §11.1's parts joined by board_a11y_separator; nothing else is set:
            onClick(label = tapLabel) { onCellTap(position); true }   //   no role, no selected, no stateDescription (D-TB)
            customActions = jumpActions                   // §4
            traversalIndex = index.toFloat()              // row-major within the slab's traversal group
            set(BoardCellPositionKey, position)           // test-only, like PegCountKey
        }
        .focusRequester(cellRequesters.getValue(position))
        .focusable(enabled = touchExploration)             // §6 — the input-focus route, enabled only while TalkBack runs (Amendment 1, A1.1 item 2); removed under F-TB-1's fallback

`tapLabel` is `null` where §11.1's table has "None", and `onClick` is still set: a cell whose tap changes nothing still activates, and the rejection is spoken. The overlay's own node carries only the test tag.

**The board stop (`Modifier.boardStop`, in `BoardCellOverlay.kt`, applied by the hosts).** §11.1: "The board stop covers the slab, so a touch on the slab's rim finds the board." The slab is the host's `Surface` (`GameScreen.kt:213-225`, tagged `GAME_BOARD_SLAB_TEST_TAG`; `TutorialScreen.kt:245-253`), outside `BoardCanvas`'s padded bounds, so the stop is a one-line modifier on each slab:

    Modifier.boardStop(pegsLeft = state.board.pegCount, focusRequester = boardStopFocus, focusEnabled = touchExploration)
        = .focusRequester(focusRequester).focusable(enabled = focusEnabled)
          .semantics { isTraversalGroup = true; contentDescription = boardLabel; onClick(label = null) { true } }
          // board_a11y_label; no role; the consumed no-op click is required from B2 (Amendment 1, A1.1 item 1 — supersedes "no onClick"); focus gated (A1.1 item 2)

Traversal is then slab stop → (its children: the board root, the Canvas, the overlay, none of them a stop) → cells in `traversalIndex` order → the next sibling (Undo on gameplay, the caption in the tutorial). Explore-by-touch on a cell finds the cell (the deepest node under the point); on the rim it finds the slab.

**What `GameScreen.kt:193-207`'s three custom keys do.** Nothing new: they stay on the `GAME_STATE_TEST_TAG` Box, are not speakable, and are not the cells' semantics (D-TB, §11.1 last paragraph).

## 3. The speech model — domain state to words, with no Android in `:domain` and no solver in the model
**Where.** `app/src/main/java/com/app/pegsolitaire/ui/components/BoardSpeech.kt` — plain Kotlin in the UI layer, **no `android.*` or `androidx.*` import**, so its tests run on JUnit without Robolectric. `:domain` is not touched: it already provides everything the model reads (`Board`, `Cell`, `Position`, `Move`, `RulesEngine.legalMoves`), and `TutorialViewModel` already calls `RulesEngine` directly, so a UI-layer call to the engine is the codebase's existing shape. The engine is called to **describe**; it never decides — every tap and action still goes through `onCellTap`, where the ViewModel re-derives the move from `legalMoves` (T-03-01).

**The types.**

    data class BoardSpeech(val pegsLeft: Int, val cells: List<CellSpeech>)          // cells in stop order: (row, col) ascending
    data class CellSpeech(
        val position: Position,
        val content: CellContent,            // Peg | Empty — Cell.Blocked never appears
        val selected: Boolean,
        val jumps: Int?,                     // a peg's legal jumps as the engine counts them; null on a hole
        val jumpTarget: Boolean,             // selected != null && position in legalTargets && content == Empty
        val hint: HintMark?,                 // Source on hintSource, Target on hintTarget, else null
        val tap: TapLabel?,                  // Select | PutDown | JumpHere | null, §11.1's table
        val actions: List<JumpAction>,       // §4's rule; sorted Up, Down, Left, Right
    )
    data class JumpAction(val direction: JumpDirection, val to: Position)
    enum class JumpDirection { Up, Down, Left, Right; companion object { fun of(from: Position, to: Position): JumpDirection } }
    object BoardSpeechModel {
        fun of(board: Board, selected: Position?, legalTargets: List<Position>, hintSource: Position?, hintTarget: Position?): BoardSpeech
        fun tapsForJump(selected: Position?, from: Position, to: Position): List<Position>   // [from, to], or [to] when selected == from
    }

The five inputs are TB-12's whole list ("the board, the selection, `legalTargets`, the move just made or undone, and the revealed hint"); the move just made or undone is the announcer's input (§5), not this model's. `jumps` comes from `RulesEngine.legalMoves(board).groupBy { it.from }`, computed once per `BoardSpeech`, not per cell. `JumpDirection.of` reads `to.row < from.row` as Up, `>` as Down, `to.col < from.col` as Left, `>` as Right — §11.1's "up is towards row 1". **The actions are sorted by `JumpDirection.ordinal`**, because the engine's sorted enumeration yields up, left, right, down for one peg and the contract lists up, down, left, right.

**The format layer** (`BoardSpeechFormat.kt`, beside it; Android `Resources` in, strings out; tested under Robolectric by the overlay and announcer tests, plus one small table test of its own):
- `cellDescription(cell)` joins, in §11.1's order and only the parts that apply, `board_a11y_position` (row + 1, col + 1), `board_a11y_peg` / `board_a11y_empty`, `board_a11y_selected`, `board_a11y_jumps` (plurals) / `board_a11y_no_jumps`, `board_a11y_jump_target`, `board_a11y_hint_source` / `board_a11y_hint_target`, with `board_a11y_separator`;
- `tapLabel(TapLabel)` → `board_a11y_action_select` / `board_a11y_action_put_down` / `board_a11y_action_jump_here`;
- `jumpActionLabel(JumpAction)` → `board_a11y_action_jump` with one of `board_a11y_direction_up/down/left/right`;
- `boardLabel(pegsLeft)` → `board_a11y_label` over `board_a11y_pegs_left` (plurals);
- `announcement(BoardEvent)` → §5's table.

**The 1-based offset lives here and nowhere else**: `Position` stays 0-based everywhere in code and tests, and `BoardSpeechFormat` adds 1 through one named constant. The model never sees a string, so a wording change touches `strings.xml` and this file only.

**TB-12, pinned.** `BoardSpeechPurityTest` (ArchUnit, `archunit-junit4` is already a test dependency): classes whose simple name starts with `BoardSpeech` or `BoardCellOverlay` or `BoardAnnounc` depend on nothing in `..domain.solver..`, `..domain.usecase..`, `..domain.assist..` or `..domain.generator..`. The code-auditor additionally reads the constructor of `BoardSpeechModel.of` against TB-12's list.

## 4. Activation and the custom actions (M4, M5)
**The double-tap is the tap.** `onClick(label = tapLabel) { onCellTap(position); true }`. The lambda is the hoisted `onCellTap` the Canvas already calls, so TalkBack's `ACTION_CLICK` enters `GameViewModel.onCellTap` (`:797-825`) or `TutorialViewModel.onCellTap` (`:135-149`) on the same path as a finger: the same tap table, ticks, cues, haptic, undo entry and tutorial progress (TB-4). Nothing is added to either ViewModel for this.

**One custom action per legal jump.** On the cells §11.1 names — every peg with a legal jump while nothing is selected; the selected peg alone while one is selected; no hole, no jumpless peg, no other peg — the cell carries `customActions = actions.map { CustomAccessibilityAction(jumpActionLabel(it)) { BoardSpeechModel.tapsForJump(selected, position, it.to).forEach(onCellTap); true } }`. The taps are the two the contract names, a selection unless already selected and then the destination, run in order on the main thread. Both `onCellTap`s are synchronous (`MutableStateFlow.update`), so the second tap reads the first's state. There is deliberately **no normalisation** of a held-other-peg state (no put-down, pick-up, jump), because the contract offers no action there and GD-TB-5 forbids a trace two taps would not leave.

**Staleness.** The lambdas capture the `BoardSpeech` of the composition they were built in. If TalkBack invokes one after the state moved on, the ViewModel's own guards hold: `performJump` applies only a move it re-derives from `legalMoves` (`:889-893`), and anything else lands as the quiet rejected tap. A stale action can never make an illegal move; at worst it is spoken as a rejection. `remember(state.board, state.selected, state.legalTargets, state.hintSource, state.hintTarget) { BoardSpeechModel.of(…) }` keeps the model from being rebuilt on unrelated recompositions (the timer tick, the ad fields) — rules/compose.md's no-allocation rule in the hot path.

## 5. Announcements (M6, TB-6, TB-8's summary, TB-9's lines)
**One channel per board.** The node is the board root `Box` of §2 — the one `feature/audio-review` already makes a polite live region through `Modifier.wrongTapAnnouncement` on the host's `modifier` (`GameScreen.kt`, audio's diff). This branch generalises that into `BoardAnnouncement.kt` in `ui/components/` and the hosts swap the modifier: *(Amendment 1, A1.3: the node is the **Canvas** (`BOARD_CANVAS_TEST_TAG`), as on audio-review, not the Box — `BoardCanvas` takes `announcement: String?` and applies the modifier below to the Canvas inside its interactive branch; the hosts pass `announcement = announcer.current` instead of a modifier.)*

    @Composable internal fun rememberBoardAnnouncer(): BoardAnnouncer         // holds `current: String?` as snapshot state
    internal fun Modifier.boardAnnouncement(announcer: BoardAnnouncer): Modifier
        = semantics { liveRegion = LiveRegionMode.Polite; announcer.current?.let { contentDescription = it } }

`BoardAnnouncer.announce(text)` sets `current`, appending audio's zero-width `REPEAT_MARK` when the text equals the last one spoken so a repeat is still a change; it then clears `current` after audio's `ANNOUNCEMENT_HOLD_MS`, and **a clear applies only to the sentence it was scheduled for** (a generation counter), so a second event inside the hold is never cut short by the first's clear. A newer sentence replaces an unspoken one by construction, which is §11.1's "nothing is spoken late over the next event". Live regions only; `View.announceForAccessibility` is deprecated from API 36 and is forbidden here.

**The sources** are composable effects beside `GameScreen.kt`'s own per-cue effects (`SelectionSound` and its siblings), each silent on first composition and on a composition recreated with carried values. ## 6. Focus (M7, TB-7, TB-9)
**The free half: node identity.** TalkBack keeps accessibility focus on a node while that node exists. Every cell node is keyed on its `Position`, is composed unconditionally for the whole `spec`, and changes only its semantics content as the state changes — it is never removed and re-added. So "the cell activated" (after a selection, a put-down, a rejected tap, a jump by tap — the destination, the one activated) costs nothing and holds on every board whose `spec` is unchanged. The dock rows are free too: an `IconButton` keeps focus through its own click. The rows "the rescue banner rising → unchanged" and "a game won → Results" need nothing.

**The paid half: input focus (F-TB-1).** For the four moves the contract orders, each target carries `focusable()` and a `FocusRequester`, and the move is `requestFocus()` on the main thread after the announcement that goes with it *(Amendment 1, A1.1 item 2: `focusable(enabled = touchExploration)`, and every `requestFocus()` below is guarded by the same boolean from `rememberTouchExplorationEnabled()`)*:
- **A jump by action → the destination cell.** Inside the custom action, after the two taps: `cellRequesters.getValue(to).requestFocus()`. The requesters are `remember(spec) { positions.associateWith { FocusRequester() } }` inside the overlay; no API leaves `BoardCanvas` for this.
- **A tutorial step installed → the new board's board stop.** `TutorialScreen` owns `boardStopFocus`, applies it through `Modifier.boardStop`, and in `StepAnnouncements`'s effect requests it after `announce(step line)` — on steps 2 and 3 only, never on the first step *(Amendment 1, A1.1 item 3; reverses the original "including the first step (F-TB-5)")*.
- **Undo or Restart from the rescue banner → the board stop.** `GameScreen` wraps the banner's two lambdas: `onUndo = { onUndo(); boardStopFocus.requestFocus() }`, likewise Restart. The request lands before the banner leaves on the next state; the slab is still there.
- **The tutorial completed → `onboarding_got_it`.** A `FocusRequester` on the completion `Button` (already focusable: it is clickable), requested in `CompletionAnnouncement` after the done line.

Order: the announcement is set first, then focus is requested, in the same effect. Whether TalkBack then speaks "announcement, then the stop" is §11.1's device-only question; the code can only order its own two calls. `focusable()` goes **after** the `semantics` block in the chain so the cell's description is the node's and the focus semantics merge into it. If the device pass finds TalkBack not following input focus, F-TB-1's fallback applies in one commit: the four `requestFocus()` calls and every `focusable()` go, and nothing else changes.

**What is not done.** No `clickable` on cells (it would add pointer handling and a Button role), no `FocusRequester` hoisting into `GameUiState`, no reflection into `AndroidComposeView`'s node provider (kotlin-android.md forbids reflection hacks), no `announceForAccessibility`.
