<objective>
## Phase Goal (MVP user story)

**As a** peg-solitaire player, **I want to** ask for a hint that reveals a genuine next winning move and undo my last move, **so that** I can get unstuck and keep playing a puzzle that stays fair and always winnable.

## This plan's slice

Build the **production `Solver`** — the pure-`:domain` engine that powers the winning-move hint on deviation (Challenge) and on every hint (Classic), and that answers "is this position genuinely unsolvable?" for the no-win state. This is the phase's one genuinely hard, high-risk component and is isolated here (context cost) so the hint-pipeline and UI slices stay thin.

It is a **port and hardening** of the already-tested `AuthoringSolver` (test source set), not a from-scratch build: reuse its memoized symmetry-canonical DFS (`VisitedSet`, `symmetryPermutations`, `canonical`, `inwardness`, `centroidOf`) verbatim, and add (1) an arbitrary-start first-move return, (2) a node budget, (3) a cooperative `shouldCancel` + deadline hook, and drop the authoring-only jitter/restart machinery. Add a pagoda necessary-condition fast-reject so dead positions return `null` in O(cells) without search.

Purpose: ASST-01 (find the winning move) + ASST-03 (return null when genuinely unsolvable), with the D-04 budget set by measurement, not a guessed constant.
Output: `domain/solver/{Solver, SolverBudget, Pagoda}.kt` + three JVM test files that lock correctness, the pagoda invariant, and the budget headroom.
</objective>
