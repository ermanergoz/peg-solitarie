stay silent. Then add the one deliberate exception to toggle silence: flipping `soundOn` ON in
Settings plays a single confirmation pop, instant proof to the player that audio works.

which also makes it greppable and reviewable. D-12's blip must bypass the mute gate, because the
DataStore write has not round-tripped through the collected flow at the moment the blip is due.

`SettingsViewModel`, and two new test files plus a constructor update to one existing test.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| player gesture → navigation callback | The click cue wraps existing hoisted callbacks; it adds no new authority and changes no navigation argument. |
| Settings toggle → mute gate bypass | `playSoundEnabledConfirmation()` is the only path in the app that plays audio while `soundOn` is false. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-07-12 | Elevation of Privilege (policy) | `playSoundEnabledConfirmation()` gate bypass | mitigate | Exactly one call site exists, in `SettingsViewModel.onToggleSound`, guarded by `if (on)`. It is reached only from a user-initiated enable — never from a flow collector, never from a screen. Asserted by the `SettingsViewModelSoundTest` cases for the disable path and the initial-emission path. The acceptance criteria pin the call site so a second one cannot appear unnoticed. |
| T-07-13 | Tampering (behaviour) | `withClickSound` wrapper ordering | mitigate | The wrapper plays the cue and then invokes the original `onClick`; it never swallows, reorders or conditions the callback. Every positive test asserts BOTH the cue and that the original callback fired. |

The acceptance criteria assert `ui/theme/Clay.kt` contains no audio reference and that the five excluded control files contain no `withClickSound`, so a future "simplification" onto the shared modifier fails the plan's own checks. |
