<objective>
Collapse the three verbatim copies of `symmetryPermutations`/`canonical` into one implementation,
add the chunked fast path the bitboard solver needs, and put a property net under it.

RESEARCH §Don't Hand-Roll and Open Question 5 both call this out, and Pitfall 4 records a REAL bug
the researcher hit from exactly this duplication class: a chunked canonicaliser that handled only
chunks 0-4 silently dropped bit 40, corrupting a Diamond-41 search into "reaching" one peg — a state
the GF(4) invariant proves impossible.

Purpose: the bitboard rewrite (plan 08-05) is about to add a fourth, faster canonicaliser. Doing
that on top of three existing copies with no correctness net is how the phase ships a silently wrong
solver. This plan is the prerequisite, deliberately scoped as its own unit rather than as drive-by
refactoring inside a solver task.
Output: one `BoardCanonical`, two deleted private copies, and `CanonicalTest`.
</objective>

  <action>
Extend `BoardCanonical` with a chunked canonicalisation fast path, keeping the existing
`symmetryPermutations` and `canonical(pegs, symmetries)` public functions unchanged so every current
caller keeps compiling.

Add an internal per-spec lookup structure — name it `ChunkTables` — built by a new
`fun chunkTables(spec: BoardSpec): ChunkTables`. It holds, for each symmetry permutation, a
`[chunkIndex][byteValue] -> Long` table so a 64-bit mask is permuted with `chunkCount` array lookups
and ORs instead of one iteration per set bit.

The chunk count MUST be derived: `chunkCount = (spec.size + BITS_PER_CHUNK - 1) / BITS_PER_CHUNK`
with `BITS_PER_CHUNK = 8` as a KDoc'd private const. Do NOT hardcode a chunk count. Add a KDoc on
`chunkTables` naming Pitfall 4 explicitly: hardcoding 5 chunks covers bits 0-39 and silently drops
bit 40 on the 41-hole Diamond and bits 40-44 on Wiegleb-45, which corrupts a search into "reaching"
states that do not exist. Also KDoc the table size: `symmetryCount * chunkCount * 256` longs, which
is at most `8 * 6 * 256 = 12288` longs (96 KB) per footprint, built once and cached.

Add `fun canonicalFast(pegs: Long, tables: ChunkTables): Long` returning the lexicographically
smallest image under all symmetries, computed via the chunk tables. Its KDoc must state that it is
an exact, faster equivalent of `canonical(pegs, symmetries)` and that `CanonicalTest` gates that
equivalence.

Memoise the tables per `BoardSpec` keyed on `spec.footprint` (the structural key added in plan
08-01) — not on referential identity, so a spec rebuilt from a resume blob hits the same cache
entry. The cache MUST be BOUNDED: Challenge generates a fresh footprint per level, so an unbounded
`Map<List<Position>, ChunkTables>` grows without limit at ~96 KB per entry. Use an access-ordered
`LinkedHashMap` with `removeEldestEntry` capped by a KDoc'd private const
`MAX_CACHED_FOOTPRINTS = 6` (the five Classic footprints plus the one Challenge footprint in play),
and KDoc why the bound exists. Keep it pure Kotlin with no Android and no coroutines
(`domain/build.gradle.kts` is `kotlin-jvm` only); guard the map for reuse across threads with
`@Synchronized` or an equivalent lock rather than a coroutine primitive.

Keep detekt happy by extracting table construction into small private functions rather than reaching
for `@Suppress` (CLAUDE.md / RESEARCH §Project Constraints).
  </action>
