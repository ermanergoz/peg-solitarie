<objective>
Implement the UMP consent flow behind the `ConsentGateway` seam, initialize the ads SDK only after
consent resolves, expose the privacy-options requirement for the Settings row, and close the missing
AdMob `APPLICATION_ID` manifest gap (CONS-01, CONS-02, CONS-03, CONS-04).

Purpose: no ad can legally or technically be requested until this exists. It also produces the
`readiness` signal that D-12 reads and the `privacyOptionsRequired` flag plan 09-07 renders.
Output: `UmpConsentGateway`, an `AdsModule` inside `..platform..` holding every SDK-typed provider,
the `ConsentGateway` Hilt binding, a one-line bootstrap in `MainActivity`, and the manifest meta-data.
</objective>

    Create `UmpConsentGateway` as a `@Singleton class UmpConsentGateway @Inject constructor(...)`
    implementing `ConsentGateway`. `@Singleton` goes on the **class**, not only on the `@Binds`,
    because this object holds `_readiness`, `_privacyOptionsRequired` and the `AtomicBoolean` init
    guard — a second unscoped instance would carry a second, permanently-`Unknown` readiness flow.
    Constructor dependencies: the `@ApplicationContext Context`, the `ForegroundActivityProvider`,
    the `ConsentInformation` provided by `AdsModule` (Task 2), and `@ApplicationScope private val scope: CoroutineScope`.

    Expose `readiness` and `privacyOptionsRequired` as `asStateFlow()` views over private
    `MutableStateFlow`s, initial values `AdsReadiness.Unknown` and `false`.

    `bootstrap()` launches on `scope` and runs, in this exact order:
    1. `withTimeoutOrNull(AdConstants.ACTIVITY_WAIT_MS) { activityProvider.awaitActivity() }` — return
       and leave readiness `Unknown` if it is null. A backgrounded app may never resume and an
       unbounded await would hang the gateway forever (the provider's own KDoc requires the caller's timeout).
    2. Build `ConsentRequestParameters`, applying `ConsentDebugSettings` with
       `DEBUG_GEOGRAPHY_EEA` **only under `BuildConfig.DEBUG`**, so an EEA form can be exercised from
       a non-EEA test location. Do not add a `UMP_TEST_DEVICE_HASHED_ID` build-config field: emulators
       are test devices by default, and adding a fourth ID key would touch the Phase-6 `AdIdResolution`
       plumbing for no benefit this phase needs. Say so in a comment.
    3. `consentInformation.requestConsentInfoUpdate(activity, params, onSuccess, onFailure)` — **every
       launch, unconditionally**. This is CONS-01, and it must run before anything reads
       `canRequestAds()`: `canRequestAds()` returns `false` until `requestConsentInfoUpdate()` has run
       in the current session, so a readiness check placed first would silently disable ads on every
       device forever (Pitfall 4). Never write `canRequestAds()` as the first statement of any function.
    4. On success: `UserMessagingPlatform.loadAndShowConsentFormIfRequired(activity) { formError -> … }`.
       A non-null `formError` sets readiness `Unavailable`. Then publish the privacy-options
       requirement and call `initializeAdsIfPermitted()`.
    5. On failure (CONS-04): do **not** block play and do not surface an error. Publish the
       privacy-options requirement and call `initializeAdsIfPermitted()` anyway — it will use the
       previous session's cached consent status, which is exactly the required fallback.

    Add `private val initialized = AtomicBoolean(false)` and a private `initializeAdsIfPermitted()`:
    return early (setting `Unavailable` if readiness is still `Unknown`) when `canRequestAds()` is
    false; otherwise `if (!initialized.compareAndSet(false, true)) { readiness = Ready; return }` and
    launch on `Dispatchers.IO` to call
    `MobileAds.initialize(appContext, InitializationConfig.Builder(AdIds.admobAppId).build()) { }`,
    then set readiness to `Ready` or `Unavailable` from `MobileAds.isInitialized`. The guard is
    mandatory because two call paths reach this function (Pitfall 5), and the background dispatcher is
    mandatory because `MobileAds.initialize` is annotated `@WorkerThread` and calling it on main risks
    an ANR. Initialization is not optional in GMA Next-Gen — skipping it throws
    `UninitializedPropertyAccessException` on the first ad call.

    `publishPrivacyOptionsRequirement()` sets `_privacyOptionsRequired.value` from
    `consentInformation.privacyOptionsRequirementStatus == REQUIRED` (CONS-03). Do not infer the
    region client-side — the status is server-configured in the AdMob Privacy & messaging UI and is
    the only source of truth.

    `showPrivacyOptions()` resolves the Activity internally through the same bounded
    `awaitActivity()` and calls `UserMessagingPlatform.showPrivacyOptionsForm(activity) { … }`,
    republishing the requirement afterwards. No `Activity` appears in the signature.

    **Log nothing** about consent status, the TCF string, or ad response info — ASVS V7. Consent
    failures degrade to `AdsReadiness.Unavailable`, never to a crash, an error wall, or a log line.

    KDoc density per the house style: name CONS-01/02/03/04, D-16, Pitfalls 4/5/16, and carry a
    "do not normalise this" paragraph on the `requestConsentInfoUpdate`-before-`canRequestAds`
    ordering, because it is the single most likely thing a future reader will "simplify".

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| player (EEA) ↔ ad personalisation | Serving a personalised ad before consent is a GDPR breach; the boundary is `canRequestAds()` and it is server-authoritative |
| UMP/GMA SDK ↔ app code | Every SDK type must stop at `..platform..`; the rule is bytecode-enforced and catches Hilt codegen |
| consent state ↔ logs / persistence | Consent status and the TCF string are personal-data-adjacent and must not be logged or re-derived by the app |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-17 | Information disclosure (GDPR) | `initializeAdsIfPermitted()` | mitigate | `MobileAds.initialize` runs only when `consentInformation.canRequestAds()` is true, and only after `requestConsentInfoUpdate()` has run this session. `AdsReadiness` gates every downstream `requestRewarded`. Ordering asserted by a grep criterion, not left to review. |
| T-09-18 | Spoofing (consent state) | consent persistence | mitigate | The app never reads or writes TCF strings and never infers consent from DataStore or a geo check — `requestConsentInfoUpdate()` runs every launch and UMP owns its own state. A client-side inference would be both wrong and a compliance exposure. |
| T-09-19 | Information disclosure | logging | mitigate | ASVS V7: no `Log`/`println`/`Timber` call may name consent status, the TCF string or ad response info. Enforced by a grep acceptance criterion on the gateway file. |
| T-09-20 | Denial of service | `awaitActivity()` in `bootstrap()` / `showPrivacyOptions()` | mitigate | Every await is wrapped in `withTimeoutOrNull(AdConstants.ACTIVITY_WAIT_MS)`; a backgrounded app that never resumes leaves readiness `Unknown` (→ not offerable → free assists) rather than hanging the gateway forever. |
| T-09-21 | Elevation of privilege (architecture erosion) | `AdsModule` placement | mitigate | Every SDK-typed `@Provides` lives in `platform/ads/di/`; asserted by `PlatformBoundaryTest`, which is bytecode-based and therefore also catches the Hilt-generated component (Pitfall 14). |
| T-09-22 | Tampering (build integrity) | manifest app ID | mitigate | The tag references `@string/admob_app_id`, a per-build-type generated resource, so a debug build can never carry the production app ID and `adIdLiteralCheck` has nothing to catch. Phase 6's `BuildConfigIdsTest` debug-prefix assertion stays green. |
| T-09-SC | Tampering | package-manager installs | accept | No packages installed. `ads-mobile-sdk 1.4.0` and `user-messaging-platform 4.0.0` are recorded **Approved** in RESEARCH.md's audit table — first-party Google Maven coordinates verified by direct maven-metadata inspection and on the graph since Phase 6 plan 06-09. Any diff reintroducing `com.google.android.gms:play-services-ads` is a typosquat-adjacent regression, not a fix. |
