<objective>
Turn the auto-grant seam into a real economy: a free per-level allowance (ADS-02), an explicit opt-in
offer once it is spent (ADS-01), a fail-open free grant when no ad can be served (ADS-03), silence
when ads are knowably unservable (CONS-04/D-12), and persistence that survives a retry and process
death (D-04/D-17).

Purpose: this is the plan the ROADMAP's locked ordering exists for — every one of these behaviours is
built and proven against the still-in-place `NoOpAdGateway` and the test fakes, **before** any real ad
SDK is wired in. The stub's silent auto-grant is exactly what currently hides the missing opt-in UI.
Output: the assist funnel and both offer callbacks in `GameViewModel`, snapshot round-tripping of the
counters, and a dedicated allowance test class.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| player ↔ rewarded-ad economy | AdMob's rewarded-inventory policy governs when an ad may play and what declining may cost; violations are account-level risks |
| restored snapshot → in-memory allowance | The counters arrive from untrusted storage through `SnapshotMapper` and become the live economy |
| ad SDK outcome → reward grant | A reward must follow a completed view, and only a completed view |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-32 | Repudiation (policy violation) | `enterAssistFunnel` step 3 | mitigate | An ad is only ever requested from `onAcceptAdOffer`, which only runs from an explicit player tap on a dialog that already named the reward. `grep` criterion pins `requestRewarded` to exactly one call site. AdMob: "must only be served after a user affirmatively and unambiguously opts in". |
| T-09-33 | Repudiation (policy violation) | `onDismissAdOffer` | mitigate | Declining mutates nothing — no counter, no board, no ticker. AdMob: "skipping … or selecting the 'no' option must not impede or interfere with the normal usage of the app". Pinned by the dismiss test asserting board, history and both counters unchanged. |
| T-09-34 | Elevation of privilege (against the advertiser) | `Granted` branch | mitigate | The ViewModel refills only on `RewardOutcome.Granted`, and the gateway sets `Granted` only from the SDK's earned-reward callback (enforced in plan 09-10). An unearned early dismiss arrives as `Declined` and refills nothing — pinned by the Declined test. ADS-05. |
| T-09-35 | Tampering (economy) | forged snapshot counters | mitigate | `applyRestored` takes `restored.allowance`, which `SnapshotMapper` produced through `AssistAllowance.fromStoredOrFull` — out-of-range values were already rejected in plan 09-01. The ViewModel never reads the raw DTO ints. |
| T-09-36 | Tampering (economy) | retry-to-farm loophole | mitigate | `resetToInitial()` deliberately does not touch `allowance`, so restarting a level cannot refill it (D-04). Pinned by the restart test. The one accepted residual hole (restart then force-kill before `ON_STOP`) is documented in code, not hidden. |
| T-09-37 | Denial of service (UX dead end) | `Unavailable` outcome | mitigate | `Unavailable` grants the assist and shows a transient explanation; `rewardedOfferable == false` grants it silently. Both paths are pinned by tests. The player is never dead-ended by an ad that failed to arrive. |
| T-09-38 | Information disclosure | D-12 silence | accept | When ads are unservable the app shows nothing at all rather than reporting a consent or SDK failure. Deliberate: surfacing that state would leak system detail to a puzzle player about a system they were never told existed, and it is what makes v1.0 parity exact. |
| T-09-SC | Tampering | package-manager installs | accept | No packages installed. RESEARCH.md's audit table records both phase artifacts as **Approved**. |
