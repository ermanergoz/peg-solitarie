<objective>
Freeze the elapsed-time ticker for the full duration of every ad presentation and resume it on
dismiss, so watching an ad can never cost the player score (ADSF-01).

Purpose: ADSF-01 is owned by this phase and re-asserted as an acceptance criterion in Phase 10, so
the mechanism must be correct and independently tested before the dialog and the funnel are built on
top of it. It wraps the two `adGateway.requestRewarded(...)` call sites that **already exist** in
`GameViewModel`, which means it can be built and proven against the current code with the existing
`GatedAdGateway` harness — no dialog required.
Output: `frozenForAd` + `freezeClockForAd()` + `unfreezeClockAfterAd()` in `GameViewModel`, a guard in
`resumeTickerIfNeeded()`, and a dedicated virtual-time test class.
</objective>

  <action>
    Add `private var frozenForAd = false` beside `tickerJob` (`GameViewModel.kt:258`), and two private
    functions next to `resumeTickerIfNeeded()`:

    `freezeClockForAd()` — returns immediately if `startMark == null` (the timer never started, so
    there is nothing to freeze and rebasing would invent time). Otherwise sets `frozenForAd = true`,
    cancels and nulls `tickerJob`, and folds the time already earned into the base with
    `elapsedBaseSeconds = _uiState.value.elapsedSeconds`.

    `unfreezeClockAfterAd()` — returns immediately unless `frozenForAd`; clears the flag; returns if
    `_uiState.value.status != GameStatus.Playing` (the game may have finished or the screen left
    while the ad was up); otherwise takes a **fresh** `startMark = timeSource.markNow()` and
    `tickerJob = launchTicker(startMark!!)`. The mark must be fresh: reusing the pre-ad mark is
    exactly how the ad's duration gets silently re-added.

    Add `if (frozenForAd) return` as the **first line** of `resumeTickerIfNeeded()`
    (`GameViewModel.kt:756`). This is not defensive: `onUndo()` ends by calling
    `resumeTickerIfNeeded()` at line ~878, and that is precisely the D-08 rescue-banner path where an
    ad may have just played. `resumeTickerIfNeeded()` reuses the *old* `startMark` and only checks
    `tickerJob != null`, so without the guard it re-adds the ad's whole duration.

    Wrap both existing `adGateway.requestRewarded(...)` call sites — in `onUndo()` (:825-840) and in
    `onHintRequested()` (:937-962) — so `freezeClockForAd()` runs immediately before the call and
    `unfreezeClockAfterAd()` immediately after it returns, on every branch of the three-way
    `RewardOutcome` `when` including `Declined`. Do not change any branch body and do not change the
    order of any other statement in this task; plan 09-06 re-orders those call sites for ADS-06 and
    the allowance funnel, and this plan must leave a clean diff for it to build on.

    Freeze from the *request*, never from a dialog being on screen (Pitfall 9): the game uses
    time-decay scoring, so a clock that stops while an offer dialog sits open is a real scoring
    exploit — a player could park the dialog indefinitely. Request-to-return is bounded by
    `AdConstants.ACCEPT_WAIT_MS` plus the ad's own duration, which is exactly what ADSF-01 means by
    "the duration of any ad presentation". Record that reasoning in a comment at `freezeClockForAd()`.

    Note in a comment that `elapsedSeconds` is whole seconds, so each freeze discards up to one
    sub-second remainder — in the player's favour, and accepted (Assumption A8).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| player-controllable dwell time → score | Scoring is time-decay based, so anything that stops the clock is score-relevant and must be bounded by something the player cannot extend at will |
| ad SDK callback timing → ViewModel state | The gateway resumes on an SDK callback whose timing the app does not control; the ViewModel must be correct for a return after the game has finished or the screen has been left |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-13 | Tampering (score integrity) | `freezeClockForAd()` placement | mitigate | Freeze wraps `requestRewarded` only, never the dialog. A player cannot park an open offer dialog to stop score decay; the frozen window is bounded by `AdConstants.ACCEPT_WAIT_MS` plus the ad's own duration. Pitfall 9. |
| T-09-14 | Tampering (score integrity, opposite direction) | `resumeTickerIfNeeded()` on the D-08 rescue path | mitigate | `if (frozenForAd) return` prevents the old `startMark` being reused, which would charge the player for the ad they were promised was free. Pinned by the Pitfall-10 regression test, whose KDoc names the guard. |
| T-09-15 | Denial of service (state corruption) | `unfreezeClockAfterAd()` after terminal / screen-leave | mitigate | The unfreeze refuses to relaunch a ticker when `status != Playing`, so a late SDK callback cannot resurrect a finished game's clock. Covered by test case 5. |
| T-09-16 | Tampering (integer) | `freezeClockForAd()` with `startMark == null` | mitigate | Early return when the timer never started, so the rebase cannot invent elapsed time out of an uninitialised mark. Covered by test case 4. |
