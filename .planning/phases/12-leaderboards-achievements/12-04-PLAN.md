<objective>
Stand up the build-time plumbing that carries the 7 leaderboard IDs and 20 achievement IDs
from an untracked `local.properties` (or a same-named CI environment variable) into
`BuildConfig`, and give the app one typed window onto them — `GamesIds` — exactly as
`AdIdResolution` + `AdIds` already do for the four ad/PGS-project IDs (D-17, PLAT-06).

Purpose: every later plan in this phase names an ID. `ProgressSubmitter` (12-07) cannot
submit a score without `GamesIds.Leaderboards.challengeLadder`, and the Play Console project
that will eventually mint the real values does not exist yet. This plan makes "no ID literal
in source" a build-enforced fact, makes a missing release ID a loud configuration-time
failure, and makes a fresh clone with zero configuration still build and still run the whole
JVM suite — so no downstream plan is blocked on Play Console.

Output: `GamesIdResolution.kt` + its `build-logic` test, 27 looped `buildConfigField`s per
build type, a `verifyReleaseGamesIds` execution-time backstop, a `gamesIdLiteralCheck` source
gate, 27 documented keys in `local.properties.template`, and `GamesIds.kt`.

**Explicitly NOT in this plan:** the `GamesService` seam (12-03), the `:domain` `AchievementId`
enum (12-02), and `GamesIds.of(AchievementId)` (12-07). Do not create, import, or reference
`AchievementId` here — it does not exist yet and inventing it would collide with 12-02.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer machine / CI → build output | `local.properties` values and environment variables cross into a shipped APK as `BuildConfig` string constants |
| git repository → public | anything committed here is world-readable in a fork or a leaked archive |
| debug build → Google's Play Games servers | a debug build carrying real IDs writes to the same production leaderboards as release |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-40 | Information disclosure / Tampering | Real leaderboard & achievement IDs committed to source | mitigate | `local.properties` is gitignored (`.gitignore:7`) and is asserted untracked by an acceptance criterion; only `local.properties.template` (key names + `REPLACE_ME_` placeholders) is committed; no `games-ids.xml` is created; the new `gamesIdLiteralCheck` fails `check` on any `CgkI`-shaped literal under `src/main` (Task 2E). These are not cryptographic secrets — they ship inside the APK — but a committed ID lets a fork write to this game's boards. |
| T-12-41 | Tampering | A release APK/AAB shipping `UNCONFIGURED-…` or `UNRESOLVED-…` placeholder IDs | mitigate | Two independent gates: configuration-time `GradleException` from `releaseGamesIds` on any release invocation (Task 2B), and the execution-time `verifyReleaseGamesIds` task hooked to `assembleRelease`/`bundleRelease` (Task 2D), because the task-name heuristic cannot be proven exhaustive. `GamesIdResolution.present()` additionally treats an `UNCONFIGURED-`-prefixed value as absent, so a pasted debug placeholder cannot satisfy the release check. Proven by `GamesIdResolutionTest`, the only place AGP 9.1.0 permits a release-side assertion. |
| T-12-42 | Tampering | A debug build submitting to production leaderboards | accept (bounded) | D-17 and RESEARCH A3 deliberately let debug honour a configured ID: Google publishes no PGS test IDs, the PGS project registers the debug-keystore SHA-1 so debug builds *can* sign in, and pre-publication scores/unlocks are resettable per tester via the Management API.
