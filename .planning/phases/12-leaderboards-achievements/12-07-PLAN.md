<objective>
Build `ProgressSubmitter` — the one data-layer `@Singleton` (D-13) that turns stored progress into
Play Games submissions — and wire its two triggers.

It owns a persisted "submissions pending" flag, runs a `Mutex`-serialised pass that reads
`ProgressRepository.aggregate()` + `classicBests()`, feeds the aggregate to
`AchievementRules.evaluate` (D-11 — one rule set for both live solves and backfill), and issues
`submitScore` / `unlockAchievement` / `setAchievementSteps` through the Boolean-returning seam that
plan 12-03 reshaped. The flag is set when the session is not `SignedIn` or when any call fails, and
cleared only when every call succeeded (D-10). A session collector, started explicitly from
`MainActivity.onCreate` so Hilt's lazy `@Singleton` cannot leave it unconstructed (RESEARCH
Pitfall 5), re-runs the pass whenever the session resolves to `SignedIn` while the flag is set —
that is the whole of PGSL-05.

Purpose: this is the plan where the phase's twelve preceding files become an observable behaviour.
Every leaderboard requirement (PGSL-01/02/03) and every achievement-delivery requirement
(PGSA-02/03) is closed here, and PGSL-04's promise — a failed submission never fails, blocks, or
alters a solved level — is a property of the two lines this plan adds to `ResultsViewModel`.

Output: two new production files (`ProgressSubmitter`, `SubmissionSyncStore`), one new DataStore
key, `GamesIds.of(AchievementId)`, one line in `ResultsViewModel`, one line in `MainActivity`, one
new JVM test class, and new cases in two existing test classes. No new Gradle dependency, no new
Hilt module entry, no schema change.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `ProgressSubmitter` → `GamesService` → Play Games SDK | App-derived values leave the process for a Google-owned service. Everything crossing here is client-computed. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-12-70 | Denial of Service | `ResultsViewModel.recordSolvedPlayOnce` → `ProgressSubmitter.onResultRecorded` | mitigate | PGSL-04 is structural, not defensive: `onResultRecorded()` is non-suspend and its entire body is `scope.launch { }` on the `@ApplicationScope`, so the Results coroutine cannot be delayed, cancelled or thrown at by a submission. Every seam call inside the pass is `runCatching`-wrapped (cancellation rethrown), and `PlayGamesService.submitting` is already Activity-wait-bounded by `GamesConstants.ACTIVITY_WAIT_MS` (12-03, T-12-32) so no call can hang unboundedly. | T-12-71 | Information Disclosure | `ProgressSubmitter.submitAll` session gate | mitigate | The pass short-circuits on `session.value !is SignedIn` before touching the repository or the SDK, and `GamesSignInState.Unknown` takes that same branch (RESEARCH Pitfall 8) — no submission is attempted for a player whose identity has not resolved, and no aggregate is even read. Tested by the `SignedOut` and `Unknown` cases, both asserting zero recorded calls. |
| T-12-72 | Tampering | Concurrent passes racing the flag write | mitigate | `submitAll()` runs under `passMutex.withLock`, so a solve landing while sign-in resolves produces two serialized passes rather than a racing pair whose flag writes could interleave and lose the pending state. `start()` is `AtomicBoolean.compareAndSet`-guarded so a second call cannot create a second collector. The SDK operations are idempotent by construction — absolute `setSteps` (D-12/D-03) and `unlock` on an already-unlocked achievement — so a duplicated pass is a no-op rather than a double count (RESEARCH Pattern 1/4). | T-12-73 | Tampering | Client-computed leaderboard scores | accept (residual) | Every submitted value is a deterministic recompute from stored aggregates (`MAX(CAST(levelId))`, `SUM(bestScore)` per D-07) rather than a running in-memory total, so a resubmission always reproduces the same number and cannot drift from the stored history. It does NOT prevent forgery: a player who edits `level_result` on a rooted device gets the scores their edited history implies. Accepted per PITFALLS.md's standing answer for a local-first single-player game — the only real fix is a server this milestone does not have.
