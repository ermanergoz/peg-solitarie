<objective>
The SDK plumbing: open the one named snapshot with `RESOLUTION_POLICY_MANUAL`, resolve any conflict
by merging both sides, read or write the bytes, and close the handle exactly once — all behind the
seam, with every gms type confined to this file.

Purpose: `RESOLUTION_POLICY_MOST_RECENTLY_MODIFIED` is the single most damaging line of code
available in this phase; Google's own javadoc says of it that "a player's changes may get lost",
while it says of MANUAL that it "ensures that no user changes to the state of the save game will
ever be lost". The ROADMAP's mandate is Google's own wording, and this plan is where it is honoured.
Output: one platform class, the Hilt binding flip, and a MockK-driven test of the open/conflict/close
lifecycle.

**Discretion resolved (the PATTERNS flagged decision, Activity accessor):** the cloud store uses the
**awaiting** accessor — `withTimeoutOrNull(GamesConstants.ACTIVITY_WAIT_MS) { activityProvider.awaitActivity() }`
— not `PlayGamesService.submitting`'s no-wait `activityProvider.current`. The reason is the pull: it
fires once per process immediately after `SignedIn` resolves, on a cold start where Home may not have
attached yet, and a no-wait read would simply skip it forever (Pitfall 3). A submission is
fire-and-forget and can afford to be skipped; the once-per-process pull cannot. A timeout is a failed
pass: return `null`/`false`, publish nothing, leave the caller's marker set.
</objective>

Private `suspend fun resolveToOpenSnapshot(client: SnapshotsClient, initial:
DataOrConflict<Snapshot>, mergeRemote: (ByteArray, ByteArray) -> ByteArray): Snapshot?` — the bounded
loop. Iterate at most `CloudSaveConstants.MAX_CONFLICT_RETRIES` times: return `result.data` as soon
as `!result.isConflict`; otherwise read `conflict.snapshot.snapshotContents.readFully()` (the
**server's** version) and `conflict.conflictingSnapshot.snapshotContents.readFully()` (the
**modified** version), call `mergeRemote(server, mine)`, `writeBytes` the merged array into
`conflict.resolutionSnapshotContents`, and `client.resolveConflict(conflict.conflictId,
conflict.snapshot.metadata.snapshotId, SnapshotMetadataChange.EMPTY_CHANGE,
conflict.resolutionSnapshotContents).await()`. Exhausting the loop returns `null`.

Three things the KDoc must state because getting them wrong is silent:
1. The loop's exit value is an **open** snapshot. `resolveConflict` has already written the merged
   bytes server-side, but the returned `data` is a handle that still must reach `commitAndClose` or
   `discardAndClose`; leaving it open blocks the next `open` for the rest of the process (Pitfall 1).
2. `EMPTY_CHANGE` during resolution, real metadata only at the final commit — the javadoc says values
   absent from a metadata change resolve to the server's current version, so a half-built change
   mid-loop would fight the final commit.
3. `getSnapshot()` is the server's version and `getConflictingSnapshot()` is the modified one. The
   merge is commutative, so swapping them is harmless **today** — which is exactly why the test pins
   the orientation, so a future non-commutative field cannot be added silently.

`override suspend fun load(mergeRemote: (ByteArray, ByteArray) -> ByteArray): ByteArray?` — await the Activity (return `null` on timeout), then
inside a `runCatching`: `PlayGames.getSnapshotsClient(activity)`, `open(SNAPSHOT_NAME, true,
RESOLUTION_POLICY_MANUAL).await()`, `resolveToOpenSnapshot(...)`, and in a `try { … } finally { … }`
read `snapshot.snapshotContents.readFully()` and return `bytes.takeIf { it.isNotEmpty() }`, with the
`finally` calling `discardAndClose` — a pure read must not rewrite the snapshot and move its
`lastModifiedTimestamp`. Track closure with a local `var closed = false` so the `finally` cannot
double-close (Pitfall 2: `commitAndClose`/`discardAndClose` fail the Task on an
already-closed snapshot). Finish with
`.onFailure { if (it is CancellationException) throw it }.getOrNull()` — the WR-04 classification.
`load`'s own `mergeRemote` parameter is the caller-supplied merge, passed straight through to
`resolveToOpenSnapshot`. KDoc why a *read* needs a merge at all: `resolveConflict` writes the merged
bytes to the server, so resolving a conflict encountered on a pull with anything other than the real
merge would discard one device's progress during what the player experiences as a restore.
