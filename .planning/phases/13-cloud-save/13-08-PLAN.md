<objective>
Join the cloud pull and push to the one orchestration point that already exists. `ProgressSubmitter`
owns the single session collector, the single pass mutex and the persisted dirty flag; D-01 and D-02
explicitly join that object rather than adding a second collector, which the class's own KDoc
documents as a race (WR-01).

Purpose: this is where the phase's ordering guarantees live, and where the single most damaging
mistake is available — running the pull **before** the profile gate would merge a new account's data
into the old account's local store, unrecoverably, and is exactly the data loss the dialog exists to
prevent (Pitfall 8).
Output: a restructured pass, a `profileSwap` state the Home screen consumes, the D-14 resolution
path, and the orchestration test.

**Discretion resolved:** one pass drains both the Phase 12 submissions and the cloud push, as two
separately-flagged serialized steps inside the same `withLock` body. A successful import that changed
anything sets the submissions dirty flag **before** the Phase 12 step in the same pass, so a restored
player's leaderboards catch up immediately rather than lagging until their next solve.

**The A7 change, stated explicitly.** Today `if (onlyIfPending && !pending) return@withLock` sits
above everything, so a signed-in player with a clean flag makes no calls at all (PGSL-05 / D-10).
That early return must become a per-step condition, because it would otherwise skip the
once-per-process pull for exactly the new-device player D-02 exists for. The *submission* half keeps
its "clean launches make no calls" property unchanged; the *cloud* half deliberately does not. This
is a reviewed change to a documented invariant, not a side effect — say so in the KDoc.
</objective>
