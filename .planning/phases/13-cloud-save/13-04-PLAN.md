<objective>
The wire format and the decode boundary. `data/cloud/` owns `@Serializable`, the `schemaVersion`
gate, per-row validation of untrusted network input, and the encode-measure-trim loop that keeps a
payload inside the Saved Games size cap.

Purpose: the cloud payload is **untrusted input arriving over the network** (ASVS V5). This is where
it is bounded — the same discipline `06-02-PLAN` applied to the resume blob's coordinates (WARN-02).
It is also where D-07's forward/backward compatibility contract is expressed, and where CLOUD-04 is
made structural: a payload type that has no board field cannot leak one.
Output: three new files under `data/cloud/` and their test.

**Discretion resolved:** payload field names are `schemaVersion` / `ladder` / `playedTimeMs` /
`bests[]{mode,levelId,stars,bestTimeMs,bestScore}`; the trim threshold is the documented 3 MB floor
minus a 256 KB margin; the trim's proof is a JVM test at an artificial 64 KB cap over a 10,000-row
payload.
</objective>

  <action>
Add `fun encodeWithinCap(progress: CloudProgress, maxBytes: Int = CloudPayloadLimits.TRIM_TARGET_BYTES):
ByteArray` to `CloudProgressCodec`.

Shape: encode once; while `encoded.size > maxBytes`, count the CHALLENGE entries in the current
`CloudProgress`; if that count is 0, **return the current encoding as-is** (the honest failure —
Classic rows plus the ladder alone exceeding the cap is impossible at five rows, and losing a
player's Classic progress to satisfy a byte budget would be the wrong trade); otherwise compute a
drop count proportional to the overshoot
(`maxOf(1, challengeRows * (encoded.size - maxBytes) / encoded.size + 1)`), apply
`ProgressMerge.dropLowestChallenge`, and re-encode. Every iteration removes at least one Challenge
row and Classic rows are never candidates, so the loop terminates in at most `challengeRowCount`
iterations — state that termination argument in the KDoc, because it is the only thing standing
between this and an infinite loop on a pathological cap.

Point `mergeBytes` at `encodeWithinCap` rather than `encode`, so a conflict resolution can never
produce a payload larger than a push would.

Extend `CloudProgressCodecTest` with the `<behavior>` cases. Build the 10,000-row fixture
programmatically (`(1..10_000).associate { … }`), and assert the "highest survive" property by
checking that the minimum surviving Challenge level is strictly greater than the maximum dropped
one. Assert the bound explicitly: capture the encode count with a counter around a test-local wrapper
or assert the test completes — prefer asserting `result.size <= cap` plus a Classic-rows-intact
assertion over timing.
  </action>
