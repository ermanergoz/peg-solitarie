<objective>
The contract everything else in the phase is written against: a `CloudSaveStore` seam that carries
**bytes in and bytes out**, plus the scoped constants, the silently-degrading stub, and the recording
fake that lets every JVM test drive the cloud path — including the conflict merge — without the SDK.

Purpose: `PlatformBoundaryRules.onlyPlatformDependsOnPlaySdks` is bytecode-based and also covers the
Hilt-generated component, so a `Provider<SnapshotsClient>` field anywhere would fail the gate. A seam
whose every signature names only Kotlin/JVM types is what keeps that structural. `GamesService`'s own
KDoc states that cloud save arrives "as a second data source behind `ProgressRepository`, not as a
method on this seam" — this plan honours that literally.
Output: three production files under a new `platform/games/save/` package, one Hilt binding, and
three test files.

**Discretion resolved:** the seam is a sibling `CloudSaveStore` in `platform/games/save/`, not a
`saveToCloud()` on `GamesService`. Snapshot identity is one fixed name, `"progress"`, with
`createIfNotFound = true`; "multiple snapshots exist" is not handled beyond picking that name,
because the requirements reserve exactly one dialog and it is the profile swap.

**Temporary binding, deliberately.** This plan binds `NoOpCloudSaveStore`; plan 13-09 replaces that
binding with the real `PlayGamesCloudSaveStore`. Binding the stub now is what lets wave 3's
`ProgressSubmitter` work compile and run green before the SDK plumbing exists. Say so in the KDoc so
a reader of the intermediate commit does not think cloud save shipped disabled.
</objective>

`CloudSaveStore.kt` — the interface and `CloudSaveDescription` as given in `<interfaces>`. KDoc must
carry, in the `GamesService` voice:
- That this interface names **no** Activity type and **no** Play Games SDK type in any signature, so
  no ViewModel or repository can obtain one through it, and that the rule is enforced by
  `PlatformBoundaryRules` at bytecode level including the Hilt-generated component.
- `load(mergeRemote)`: `ByteArray?` where `null` means "there is none, or it could not be read" and the caller
  must read that as **stay local** (CLOUD-05) — explicitly **not** "the player has no progress". It
  never throws: offline, no Activity, Play Console misconfigured and contents-unavailable all
  collapse to `null`.
- `save()`: `Boolean` where `false` means "nothing reached the cloud" and is **not an error** — the
  caller sets the persisted pending marker and retries next pass (D-01), exactly as `submitScore`'s
  KDoc describes for submissions.
- `mergeRemote`: why it is a parameter on **both** methods rather than something the platform layer
  knows. It is a pure, synchronous `(ByteArray, ByteArray) -> ByteArray` supplied by `data/cloud`,
  and it is the only way the conflict path can reuse the same merge as the local path without
  `platform/` learning what a `CloudProgress` is. `load` needs it too: an `open` can come back
  conflicted on a read, and resolving that conflict writes merged bytes to the server — resolving it
  with anything other than the real merge would discard one device's progress on a *pull*.
- `CloudSaveDescription`: three ints, **not** a formatted string, so `data/` never touches a
  `Context` and the description stays in `strings.xml` and follows the device locale at commit time
  (D-11). Name plan 13-07's formatter as the only consumer.
- One paragraph recording RESEARCH Pitfall 4 so a future reader does not "fix" it: Play Games caches
  an offline `commitAndClose` locally and syncs on reconnect, so `save` can legitimately return
  `true` before anything reaches the server. The data is not lost — GMS owns that retry, and there is
  no API to observe it. Adding an app-level upload check would duplicate a queue Google already runs.

`CloudSaveConstants.kt` — `object CloudSaveConstants` with `const val SNAPSHOT_NAME = "progress"`,
`const val MAX_CONFLICT_RETRIES = 10`, `const val COVER_PX = 512`,
`const val MAX_DESCRIPTION_CHARS = 100`. Every member KDoc'd with *why that value*:
- `SNAPSHOT_NAME` — one fixed name per player (the discretion resolution above); the SDK requires
  1-100 characters from `[A-Za-z0-9-._~]`, quoted in the KDoc.
- `MAX_CONFLICT_RETRIES` — `resolveConflict` is documented to be able to produce a conflict itself;
  10 is Google's own sample bound, and exhausting it is a clean failure, not a crash.
- `COVER_PX` — 512 matches the launcher art's native 512-unit design canvas exactly, so there is no
  resampling (plan 13-07); note that if UAT test 12's measurement ever looks close to the 800 KB
  cover ceiling, this is the one constant to lower.
- `MAX_DESCRIPTION_CHARS` — no maximum is documented anywhere for `setDescription`
  (RESEARCH assumption A2); this is a defensive truncation guard so an over-long description can
  never reject the whole commit. The D-11 one-liner is ~45 chars, so it never bites in practice.
detekt's `MagicNumber` is active over `src/main` with only -1/0/1/2 exempt, so all four must be
`const val`s here and nowhere else.
