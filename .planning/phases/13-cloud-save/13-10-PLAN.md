<objective>
The one dialog the v1.1 requirements reserved. When `session` resolves to `SignedIn` with a player id
different from the one this device's progress was last merged with, the player is asked — once, on
Home — whether to keep this device's progress or adopt the new account's.

Purpose: every other conflict in this phase resolves silently by monotonic merge. This one cannot,
because merging two different players' progress is not a merge, it is a leak. The dialog's job is to
make the safe answer effortless: the destructive option must be the deliberate one.
Output: a stateless clay dialog modelled on the Phase 11 opt-in prompt, two `HomeUiState` peers, the
ViewModel wiring, and the tests that prove the two first-run surfaces and this one never stack.

**Discretion resolved (the PATTERNS flagged decision, which button gets the gradient CTA):** the
gradient primary goes on **"Keep this device's progress"** with `SoundCue.ButtonForward`, and the
destructive "Use their cloud progress" is the `TextButton` with `SoundCue.ButtonDismiss`. This is the
inverse of the opt-in prompt's arrangement, deliberately: there the gradient carried the affirmative
action, here it carries the *safe* one, because D-13 makes non-destruction the default and a gradient
on a wipe is a trap.

**Discretion resolved (HomeUiState flag shape):** two peer fields — `profileSwapVisible: Boolean` and
`profileSwapAccountName: String?` — not one nullable field. `GamesSignInState.SignedIn.displayName`
is legitimately nullable (Phase 11 D-14: a failed name lookup is not a failed sign-in), so a single
nullable-carrying field could not distinguish "visible, name unknown" from "not visible".
</objective>
