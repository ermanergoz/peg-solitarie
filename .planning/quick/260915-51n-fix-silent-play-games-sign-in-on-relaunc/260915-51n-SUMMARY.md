# Quick Task 260915-51n: Fix silent Play Games sign-in on relaunch — Summary

**An opted-in player's cold relaunch now restores the session with no tap, because `PlayGamesSdk.initialize` moved from a coroutine off `MainActivity.onCreate` to `App.onCreate` behind the same persisted opt-in gate — early enough for the SDK's automatic authenticator to see the first Activity's creation.**

## Accomplishments

### Task 1 — the seam and the call site (`5f337ee` RED, `5ddd120` GREEN)

`GamesService` gained `initializeIfOptedIn()`, documented to the same standard as its
neighbours: it runs at process start from `Application.onCreate`, before any Activity exists;
it is gated on the persisted opt-in flag exactly as `bootstrapIfOptedIn` is (D-07/D-17); it
reads that flag synchronously because the decision must be made before the first
`onActivityCreated`; and it is not `suspend` and performs no sign-in work of its own.

`PlayGamesService` implements it: `@param:ApplicationContext appContext` added to the
constructor (the `UmpConsentGateway` convention), a second `AtomicBoolean` (`sdkInitialized`)
beside `bootstrapped`, and a body wrapped in `runCatching` that reads
`runBlocking { optInRepository.optedIn.first() }`, returns untouched when it is false, and
otherwise calls `PlayGamesSdk.initialize(appContext)` under `compareAndSet(false, true)`. No
`sdkMutex`, no session write. `bootstrapIfOptedIn` and `signIn` are behaviourally unchanged;
both had their KDoc extended to say why they still call `initialize` themselves (the D-19
first-ever-opt-in-in-this-process case).

`App` injects the **interface** and calls `gamesService.initializeIfOptedIn()` between
`activityProvider.attachTo(this)` and `foregroundTracker.attach()`, with a comment recording
that the position is load-bearing in both directions. `App` still imports nothing from
`com.google.android.gms`. The manifest's `PlayGamesInitProvider` removal comment was corrected:
the removal stands, but initialize now runs at the same process-start moment the provider would
have used — gated, which is the distinction the provider cannot make.

### Task 2 — the JVM gates (`4fce1ee`)

Four new cases in `PlayGamesServiceTest`, in a `// ---- initializeIfOptedIn: the process-start
gate ----` section above the bootstrap section, reusing the existing `mockkStatic` harness and
`serviceFor` helper (now passing a `mockk<Context>()`):

| Case | Asserts |
|------|---------|
| `initializeIfOptedInForANonOptedInPlayerNeverTouchesTheSdk` | `initialize` ×0 **and** `awaitActivity()` ×0 |
| `initializeIfOptedInForAnOptedInPlayerInitializesTheSdk` | `initialize` ×1 with no `advanceUntilIdle()` — i.e. synchronous |
| `initializeIfOptedInInitializesAtMostOncePerProcess` | two calls, `initialize` ×1 |
| `initializeIfOptedInSurvivesAFailingOptInRead` | a throwing `optedIn` flow returns normally, SDK untouched |

Plus a `NoOpGamesService` stub case, a `ThrowingOptInRepository` fake beside
`SettableOptInRepository`, and `FakeGamesService.initializeCallCount` (counts only — the gate is
never re-implemented in the fake).

### Task 3 — the emulator proof (`ea8f415`)

`:app:installDebug` → `am force-stop` → `logcat -c` → launcher intent, with **no taps**. Within
~2 s Play Services logged `GamesConnectSignInOp: signIn(%s): Returning SUCCESS`, then
`SignInPerformer: Found existing game run` and `Connection from [%s], returning true for
shouldShowWelcomePopup`. Opening Settings (the only tap in the run) showed
`Signed in as …` plus the Leaderboards and Achievements rows. UAT test 1 is recorded as PASS
with that evidence; the file's header note and summary counts were corrected to agree with it
(passed 6 → 7, issues 1 → 0, and a duplicate `blocked` key removed).
