**Old asset** (`app/src/main/res/raw/sfx_star_pop.ogg`, being replaced):
vorbis / mono / 44100 Hz / container duration **0.134943 s** / 4,421 B /
peak **-3.248 dBFS**. Audible content ends around 0.090 s (-60 dB threshold). The new cue is
therefore roughly **12x** longer by container duration and ~15x by audible content.

**Intermediate** (the trim, before normalisation): mono / 44100 Hz / **1.650000 s** /
peak **-7.494 dBFS**.

**Peak matching, measured empirically.** libvorbis overshoots on this transient, so the gain
must be chosen against the *encoded* peak, not the pre-encode peak. Naively lifting the PCM
to -3.25 dBFS lands the encoded file far louder. Measured sweep of the encoded result:

| pre-encode gain | encoded peak | size |
|---|---|---|
| +1.20 dB | -3.591 dBFS | 17,702 B |
| **+1.40 dB** | **-3.338 dBFS** | **17,726 B** |
| +1.50 dB | -3.014 dBFS | 17,749 B |
| +1.60 dB | -2.944 dBFS | 17,767 B |
| +1.80 dB | -2.848 dBFS | 17,816 B |

**+1.40 dB is the value to use.** It lands the encoded peak within 0.09 dB of the old
asset's -3.248 dBFS, preserving the per-cue balance CREDITS.md documents (invalid tap
quietest at -14 dBFS, win stinger loudest at -1.5 dBFS). Peak normalisation is measured with
`astats`; **do not introduce `loudnorm`** — plan 07-01 rejected it because these cues are
far shorter than its ~3 s analysis window.

**libvorbis is NOT byte-deterministic.** Two identical invocations produced identical audio
(same peak, same 17,749 B) but different md5s (`22aa3f43…`, `da74aa7f…`). **Do not write a
byte-hash or md5 gate for the `.ogg`.** Verify it by measured properties — codec, channels,
sample rate, duration, peak — instead.

**Decoded PCM footprint:** 1.65 s x 44100 Hz x 2 B = **145,530 B** (~0.14 MB), still far
under `SoundPool`'s 1 MB per-sample limit despite the ~12x duration increase.

**Concurrency, re-checked (see Task 2).** With a 1.65 s cue at 500 ms spacing the pops
genuinely overlap: relative to Results entry, pops fire at 250 / 750 / 1250 ms and ring
until 1900 / 2400 / 2900 ms, so all three are live together between 1250 and 1900 ms. The
win stinger (`sfx_win`, 0.54 s) fires on the board *before* navigation, so it can overlap
pop 1 but has expired well before pop 2. Worst-case simultaneous voices is therefore **4**
(stinger + pop 1, or the three pops together plus a lingering stinger), against
`MAX_STREAMS = 8`. **8 holds with 2x headroom and must not be raised**; `SoundPoolPlayer`'s
oldest-first eviction at `activeStreams.size >= MAX_STREAMS` is never reached.
